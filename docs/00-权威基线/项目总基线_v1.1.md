# 1. 产品定义【冻结】

> **一个以 Zygisk 为 Android 进程入口、以 Frida-Gum + LSPlant 为 Runtime 后端、以 Network/Packet Engine 为网络数据面、以 MCP + AI Agent 为控制面的 Android 实时动态分析平台。**

核心目标不是让用户分别操作 Frida、抓包工具、内存工具和 APK 分析工具，而是：

```text
选择目标 App → App 正常运行 → Zygisk 自动进入
→ Runtime 常驻 → PC/MCP 在线控制
→ 实时 Hook / Memory / Network / Packet → AI 自动关联分析
```

**用户只需要面对：**

```text
App · Session · Runtime · Network · Packet · Memory · Hook · AI
```

**用户不需要理解的底层细节：**

```text
Frida attach · PID · Agent · RPC · Gum Context
ART Hook Backend · Packet Backend · Network Backend
Event Serialization · Correlation ID
```

# 2. 六大设计原则【冻结】

| # | 原则 | 违反后果 |
|---|---|---|
| 1 | **用户只选择 APK**，不做手动找 PID / 启 frida-server / attach / 配代理 | 产品退化成工具堆 |
| 2 | **Runtime 必须真正存在于运行中的 App**，不是离线模拟、不是纯静态 | 失去"动态分析"全部意义 |
| 3 | **Hook 必须实时生效**，创建后作用于当前运行进程，App 不重启 | 退化成离线脚本 |
| 4 | **Network 与 Runtime 必须同时存在**，双通道互补而非互相替代 | 退化成普通抓包软件或纯 Frida GUI |
| 5 | **所有数据必须能够关联**：Packet→Network→Thread→Java→JNI→Native→Module→Hook | 失去平台差异化能力 |
| 6 | **AI 是控制中心，不是聊天窗口**：能查询/定位/Hook/读写/抓包/关联/建规则/跑工作流/出报告 | 退化成问答机器人 |

# 4. Zygisk 定位【冻结】

> **Zygisk = Runtime 启动入口，不是分析逻辑载体。**

**负责：**

```text
Module Load · Target Detection · Target Matching
Process Initialization · Runtime Bootstrap · Session Bootstrap · IPC Bootstrap
```

**明确不负责：**

```text
MCP · AI · JADX · APKTool · PCAP 分析 · 复杂协议解析
大型 WebUI · Workflow Engine · Analysis Engine
```

理由：避免把整个系统逻辑堆积进 Zygisk Module，导致每次逻辑变更都要重新推包重启。

# 5. Runtime Plane【冻结】

## 5.1 进程内结构

```text
Target Application Process
└── libai_analyzer.so
    ├── Zygisk Bootstrap
    ├── Runtime Agent
    ├── Frida-Gum Backend      （Native）
    ├── LSPlant Backend        （Java / ART）
    ├── Memory Engine
    ├── Module Engine
    ├── Thread Engine
    ├── Hook Engine
    ├── Stack Engine
    ├── Event Bus（进程内）
    ├── Network Bootstrap
    └── IPC Client
```

## 5.2 Frida 集成原则

Frida 属于**底层 instrumentation backend**，平台 API 不暴露 Frida 原始 API。

```text
AI 不调用 gum_interceptor_attach()
AI 调用 runtime.hook()
      ↓ Hook Engine → Native Backend → Frida-Gum
```

未来替换 ShadowHook / ByteHook 时上层 API 不变。

## 5.3 Hook 对象模型

```json
{
  "hook_id": "hook_xxx",
  "session_id": "sess_xxx",
  "type": "native",
  "module": "libgame.so",
  "address": "0x12345678",
  "status": "active"
}
```

状态机：`pending → active → disabled → removed → failed`

必须支持：`hook.create / hook.info / hook.list / hook.enable / hook.disable / hook.remove`

## 5.4 Memory Engine

能力：`Read / Write / Search / Dump / Compare / Pointer`

> 🔴 `memory.write` 必须真正修改**目标进程内存**，不是修改数据库里的分析结果。完整路径见 §12 Write Guard。

## 5.5 Stack Engine

统一 `Java Stack → JNI Chain → Native Stack → Module → Function`，这是 Correlation 的基础。

# 6. Network Plane【冻结】

## 6.1 双通道原则

```text
              App
               │
       ┌───────┴────────┐
       ▼                ▼
Runtime Plane      Network Plane
       │                │
       │          TCP/HTTP/HTTPS
       │          WebSocket/Packet
       └───────┬────────┘
               ▼
            EventBus → Correlation
```

两边不是互相替代，而是互相补充：

> **Network Plane 负责网络侧观察，Runtime Plane 负责 App 内部运行时观察。**

## 6.2 Observation Plane vs Control Plane

```text
Observation：DNS · TCP · UDP · HTTP · HTTPS · WebSocket · Connection · Packet
Control    ：intercept · modify · continue · drop · replay

Network Event → Interceptor → Decision
                                 ├─ PASS
                                 ├─ MODIFY
                                 └─ DROP
                                      ↓
                                  Continue
```

## 6.3 HTTPS 五级状态【冻结】

> 🔴 **TCP 抓到 ≠ HTTPS 明文可修改。**

能力状态必须逐級如实上报，禁止跨级推断：

```text
captured → decoded → decrypted → interceptable → modifiable
```

```json
{
  "protocol": "HTTPS",
  "captured": true,
  "decoded": true,
  "decrypted": false,
  "interceptable": false,
  "modifiable": false
}
```

应用存在 certificate pinning / custom TLS stack 时，网络层不一定能获得明文；此时 Runtime Plane 的 TLS 明文边界观察（加密前 / 解密后）是唯一补充路径。

## 6.4 Backend 适配器

```text
Network Engine
├── PcapdroidAdapter
├── MitmproxyAdapter
├── VPNAdapter
└── RuntimeNetworkAdapter
```

上层统一对象：`HTTPSConnection / HTTPRequest / HTTPResponse / Packet`，Backend 可替换不影响上层。

# 7. EventBus 与事件模型【冻结】

## 7.1 统一事件格式

```json
{
  "version": "1.0",
  "type": "EVENT",
  "event_id": "evt_xxx",
  "session_id": "sess_xxx",
  "timestamp": 0,
  "pid": 1234,
  "tid": 1235,
  "event_type": "HOOK_ENTER",
  "source": "runtime",
  "payload": {}
}
```

每个 Event 至少含：`EventID · SessionID · Timestamp · PID · TID · EventType · Source · Payload`

## 7.2 事件清单

**第一批（P0）：**

```text
PROCESS_STARTED · AGENT_CONNECTED · RUNTIME_READY
MODULE_LOADED · THREAD_CREATED
HOOK_ENTER · HOOK_LEAVE
NETWORK_CONNECTED · HTTP_REQUEST · HTTP_RESPONSE
PACKET_CAPTURED
```

**第二批（P1）：**

```text
DEX_LOADED · CLASS_LOADED · JNI_CALL · SO_LOADED
MEMORY_CHANGED · WEBSOCKET_FRAME
HOOK_INSTALLED · PACKET_MODIFIED · PACKET_REPLAYED
```

## 7.3 Runtime / Network 不直接相互依赖

```text
Backend → Event → EventBus → Session / Correlation
```

# 8. Correlation Engine【冻结】

平台核心差异化能力。时间模型要求所有重要事件携带 `timestamp / session_id / pid / tid / connection_id`。

**标准链路：**

```text
HTTP POST /login
   ↓ Connection → PID → TID
   ↓ Runtime Event → Java Stack → JNI → Native Stack
   ↓ Module → Function
   ↓ AnalysisObject
```

**AnalysisObject 示例：**

```json
{
  "analysis_id": "analysis_001",
  "request": { "method": "POST", "url": "/login" },
  "process": { "pid": 18342 },
  "thread":  { "tid": 18350 },
  "java_stack": [], "jni_chain": [], "native_stack": [],
  "modules": [], "packets": []
}
```

AI 最终分析的是 **AnalysisObject**，不是几十个底层工具的零散日志。

# 9. Session【冻结 + v1.1 增强】

## 9.1 Session 是唯一数据边界

```text
AnalysisSession
├── Device · APK · Process
├── Runtime · Memory · Network · Packet · Hooks
├── Events · Correlations · Workflows
└── artifact_index
```

## 9.2 生命周期

```text
CREATED → STARTING → RUNTIME_READY → NETWORK_READY
       → RUNNING → PAUSED → STOPPING → CLOSED
异常分支：DEGRADED / FAILED / ERROR
```

## 9.3 看门狗（v1.1 新增）🔴

Session 必须具备：

```text
idle timeout
process death detection
device disconnect detection
socket disconnect detection
exception cleanup
```

```text
App Process Death
       ↓
Session DEGRADED
       ↓
cleanup（Hook 卸载 / 内存锁释放 / 文件句柄关闭）
       ↓
Session CLOSED
```

> 🔴 **禁止无限持有 Session。** 任何"打开→操作→关闭"三段式都必须有 TTL，忘记关闭的代价是"自动过期"而非"永久泄漏"。

## 9.4 重连规则【冻结】🔴

> **重连不恢复旧 Session。**

```text
Session A → disconnect → Session A INVALID → reconnect → Session B
```

重连后必须重建 `runtime / network / correlation` 全部状态。理由：允许"重连后继续使用旧 sessionId"会让 AI 在幽灵数据上连续推理十轮——多花 3 轮重建远优于全盘错误。

# 10. Protocol Layer v1（v1.1 决议 1）【冻结】

## 10.1 传输

```text
Unix Domain Socket
+ 4 bytes uint32（payload length，网络字节序）
+ JSON payload
```

保留 v1.0 的帧格式，v1.1 只补齐**生命周期**。

### 10.1.1 默认端点（v1.1 补记 · 2026-09-19 项目所有者裁定）

| 传输 | 默认端点 | 常量单一源 |
|---|---|---|
| UDS（冻结方案） | `/data/local/tmp/ai-analyzer/analyzer.sock` | `DEFAULT_SOCKET_PATH` |
| TCP 回环 | `127.0.0.1:60500` | `DEFAULT_TCP_HOST` / `DEFAULT_TCP_PORT` / `DEFAULT_TCP_ENDPOINT` |

TCP 是**等价回退**，不是第二协议：帧格式、消息格式、握手与重连流程两种传输完全一致。
原默认端口 `27901` 于 2026-09-19 裁定改为 `60500`。

绑定地址固定为回环 `127.0.0.1`，**不提供 host 覆盖项**。
Runtime 以 root 能力运行，监听 `0.0.0.0` 等同于把设备的内存读写权限
开放给同一网段的任何人。

真机接入（PC 侧转发）：

```text
adb forward tcp:60500 tcp:60500
python -m ai_analyzer.host --endpoint tcp:127.0.0.1:60500
```

## 10.2 连接流程

```text
CONNECT → HELLO → HELLO_ACK → READY → REQUEST / RESPONSE / EVENT
```

## 10.3 HELLO

客户端（MCP Server / PC 控制端）首先发送：

```json
{
  "type": "HELLO",
  "protocol": "1.0",
  "client": "mcp-server",
  "client_version": "1.0.0",
  "capabilities": ["runtime", "memory", "network", "packet"]
}
```

服务端回应：

```json
{
  "type": "HELLO_ACK",
  "protocol": "1.0",
  "server": "ai-analyzer",
  "server_version": "1.0.0",
  "session_id": "sess_xxx",
  "capabilities": ["native_hook", "java_hook", "memory_read", "memory_write", "packet_intercept"]
}
```

版本不兼容 → `ERROR_PROTOCOL_VERSION`，**禁止进入 READY**（避免后续每条命令静默失败）。

## 10.4 Heartbeat

```text
PING → PONG
heartbeat_interval = 5s
heartbeat_timeout  = 30s

CONNECTED → DEGRADED（单次超时）→ DISCONNECTED（连续超时）
```

> 🔴 心跳是防卡死命门。没有心跳时，调用方无法区分"在算"和"死了"，只能盲等→超时→重试→重试风暴。

## 10.5 Reconnect

```text
disconnect → 1s → 2s → 4s → 8s → 16s → 30s（上限）
```

指数退避，上限防止疯狂重连占满事件循环。重连成功必须：

```text
重新 HELLO + 校验 protocol + 重新拉取 capabilities
+ 所有 session_id 立即失效
+ in-flight 调用返回明确错误（"连接已断开，已自动重连，请重试"，不可静默吞掉）
```

## 10.6 消息三态

**REQUEST：**

```json
{
  "version": "1.0",
  "type": "REQUEST",
  "request_id": "req_xxx",
  "session_id": "sess_xxx",
  "timestamp": 0,
  "command": "runtime.hook",
  "payload": {}
}
```

**RESPONSE：**

```json
{
  "version": "1.0",
  "type": "RESPONSE",
  "request_id": "req_xxx",
  "session_id": "sess_xxx",
  "status": "ok",
  "code": "OK",
  "payload": {}
}
```

**EVENT：** 见 §7.1。

## 10.7 Command Class（必须写进协议）🔴

| 类别 | 命令 | 特征 |
|---|---|---|
| **FAST** | `process.list` `process.info` `runtime.status` `memory.read` `network.connections` `network.dns` `packet.get` | 毫秒级，命令线程直接执行，立即返回 |
| **JOB** | `memory.dump` `packet.export` `apk.decompile` `network.capture_start` `runtime.trace` `large analysis` | 秒~分钟级，投 worker 线程，返回 job |

JOB 语义：

```text
submit → job_id → job.status(progress / eta / suggested_wait_ms) → job.result
                                                                 → job.cancel
```

> 🔴 不分级 = 分钟级重活期间 `ping / status / 日志` 全部排队 → AI 误判掉线 → 触发更多重试。

## 10.8 错误分层【冻结】🟠

| 类型 | 含义 | 返回方式 |
|---|---|---|
| **协议层错误** | AI/客户端调错了（未知命令、参数校验失败、版本不匹配、JSON 解析失败） | JSON-RPC `error` |
| **执行层失败** | 调用合法但后端执行失败（读内存失败、权限被拒、进程已退出、扫描无结果） | `isError: true` tool result |

混为一谈 = AI 无法自我纠错（该改参数时它去重试，该换策略时它改参数）。

**错误码表（稳定契约，发布后只增不改义）：**

| 错误码 | 层 | AI 应做什么 |
|---|---|---|
| `ERROR_PROTOCOL_VERSION` | 协议 | 停止，报告需升级（不可重试） |
| `E_BAD_ARGS` / `E_UNKNOWN_CMD` | 协议 | 改参数 / 改工具名 |
| `E_NOT_READY` | 执行 | 先完成前置步骤（等待 RUNTIME_READY） |
| `E_SESSION_STALE` | 执行 | Session 已失效，重建 |
| `E_READ_FAILED` / `E_WRITE_FAILED` | 执行 | 查地址 / 换候选 / 查映射可写性 |
| `E_MAP_STALE` | 执行 | 模块映射已变，重新 `process.modules` |
| `E_TIMEOUT` | 执行 | 当作"后端可能异常"，先探活 |
| `E_CANCELLED` | 执行 | 重新发起 |
| `E_NOT_FOUND` | 执行 | 换搜索方式（放宽条件 / 改特征码） |
| `E_PERMISSION_DENIED` | 执行 | 报告权限不足，降级 |
| `E_INTERNAL` | 执行 | 查日志 |

> 🟡 详细错误是**功能**不是风险。本地单用户调试工具场景下，错误消息必须可行动（含地址、状态枚举、下一步建议），"操作失败"四个字会让 AI 陷入无限重试。

# 11. Tool Surface Manager（v1.1 决议 2）【冻结】

## 11.1 核心决定

> 🔴 **不为了省 MCP 工具数量而砍掉功能。**

```text
功能数量 ≠ MCP 常驻工具数量
```

原架构 50+ tools 全部保留，但不允许全部常驻暴露。

## 11.2 Core Surface（常驻 ≤25）

```text
device.list            device.info
apk.list               apk.launch            apk.stop
session.list           session.info          session.capabilities
process.list           process.info          process.modules      process.threads
runtime.status         runtime.hook          runtime.unhook       runtime.trace
memory.read            memory.write          memory.search
network.capture_start  network.capture_stop  network.connections
packet.get             packet.modify
artifact.get
```

## 11.3 Expert Surface（按需动态挂载）

| 组 | 工具 | 挂载条件 |
|---|---|---|
| Device+ | `device.shell` `device.reboot` `device.root_status` | 用户显式开启 |
| APK+ | `apk.install` `apk.uninstall` `apk.manifest` `apk.permissions` `apk.decompile` `apk.search` | 需要静态分析时 |
| Runtime+ | `runtime.attach` `runtime.enumerate_classes` `runtime.enumerate_methods` `runtime.enumerate_modules` `runtime.hook_enable` `runtime.hook_disable` `runtime.hook_info` `runtime.stacktrace` | RUNTIME_READY 后 |

## 11.4 工具命名冻结（v1.1 决议 3）【冻结】

统一 `domain.action`，**snake_case**：

```text

❌ readMemory     memoryRead      runtimeHook     Memory_Read
```

> 说明：经验文档曾建议 camelCase（token 更省）。本项目**明确选择 snake_case**，理由是与 IPC 协议命令名、事件名、代码标识符保持**单一命名源**，避免三套命名并行漂移。这是一次**有理由的偏离**，记录在案。

## 11.5 工具四件套（每个工具必备）🟠

```text
name / title / description + inputSchema + outputSchema + annotations
```

| 件 | 要求 |
|---|---|
| `description` | 含 use_case（何时调）、important_notes（前置条件 / 易错点 / **下一步调什么**）、**耗时档位**（快 <1s / 中 <30s / 慢 <5min） |
| `inputSchema` | 每个可选参数有 default；数值标 min/max；数组标 maxItems；`additionalProperties: false` |
| `outputSchema` | 每个有返回数据的工具必须声明，与 structuredContent 严格一致（单测反向校验）；地址用字符串 `"0x..."` 不用 number |
| `annotations` | `readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint` 全部显式给出 |

## 11.6 三条工具设计硬规则🟠

1. **禁止 "not found" 响应**：扫描零命中时返回放宽条件的次优候选 + 中性描述。AI 被负向表述强烈带偏，会直接放弃或乱猜。
2. **禁止负向替 AI 下结论**：解出乱码就原样返回乱码，让 AI 自己判断形态。"命中数较低" ≠ "不是"。
3. **证据内嵌**：凡"先找候选、再验证候选"的工具族，把验证证据（样本 / 评分）内嵌进候选返回，把"扫描→采样→判定"三轮压成一轮，AI 想跳过验证都跳不过去。

## 11.7 Token 预算🟠

```text
单工具响应 ≤ 4K token（违反视为 bug）
常驻工具 ≤ 25（Expert 组动态挂载）
列表类统一支持 brief 参数（brief:true 只回统计 + 前 N 条摘要）
描述瘦身：important_notes ≤ 5 条，description ≤ 150 token
```

大响应必须分页返回 `nextCursor`，并显式标 `truncated: true` + 总数。

# 12. Write Guard（v1.1 决议 4）【冻结】

## 12.1 覆盖范围

所有修改类操作统一经过 Write Guard：

```text
memory.write
packet.modify
runtime hook modification（参数 / 返回值改写）
network response modification
```

## 12.2 生命周期🔴

```text
REQUEST
  ↓
VALIDATE      （session / address / mapping / permission / size）
  ↓
PREVIEW       （original → new，差异可视化）
  ↓
BACKUP        （保存原值，支持回滚）
  ↓
CONFIRM       （显式确认参数，默认 false）
  ↓
EXECUTE
  ↓
VERIFY        （read-back 校验）
  ↓
COMMIT
失败 → ROLLBACK
```

## 12.3 Memory Write 强制路径

```text
memory.write
    ↓ address validation（地址必须落在已映射区间内）
    ↓ memory permission validation（区间权限必须含 PROT_WRITE）
    ↓ read original value
    ↓ backup
    ↓ write
    ↓ read-back verification
```

返回必须能证明三件事：

```text
original · new · verified
```

> 🔴 **写路径的校验器必须独立于读路径**，读成功 ≠ 写安全。非法地址必须 Reject + Error Event，**绝不能让 Analyzer 崩溃**。

## 12.4 Packet Modify 强制路径

```text
packet → decode → original HEX → modified HEX
      → length validation → protocol validation
      → confirm → send → result
```

不能只返回 `success`。必须保存 `original_hex / modified_hex / offset / changed_length / timestamp / rule / session`。

## 12.5 禁止 Fake Success🔴

任何执行型工具都必须区分三级：

```text
accepted（请求受理）→ executed（已执行）→ verified（已验证生效）
```

例：`runtime.hook` 返回 `{status:"ok"}` **不算成功**，必须能产生：

```text
HOOK_INSTALLED → HOOK_ENTER → HOOK_LEAVE
```

至少验证 Hook 真实进入目标执行路径。

## 13.1 范围


# 15. 双层验收（v1.1 决议 5）【冻结】

> 🔴 **任务完成 ≠ 语义正确。** `success=true` 必须配合一组语义断言才算真成功。

## 15.1 Layer 1：流程验收（Test 01–10，保留）

| # | 验收项 | 通过标准 |
|---|---|---|
| 01 | 自动注入 | 启动 APK → Zygisk 命中 → libai_analyzer.so 加载 → Session 出现 |
| 02 | Native Hook | 目标函数执行 → HOOK_ENTER → HOOK_LEAVE 真实发生 |
| 03 | Java Hook | Java Method → LSPlant → Hook Event 真实发生 |
| 04 | Memory Read | 读取实际进程地址 → 返回真实值 |
| 05 | Memory Write | 写入实际进程 → 程序继续运行 → 观察到新值 |
| 06 | Network Capture | APK → Connection → Packet 实时出现 |
| 07 | HTTP Intercept | HTTP Request → Interceptor → Modify → Forward，下游收到修改后数据 |
| 08 | HTTPS 分级 | TCP captured / TLS observed / HTTPS decrypted / HTTP visible / HTTP modifiable **逐级单独验收** |
| 09 | Packet HEX Modify | Live Packet → HEX → 修改 → Forward，验证下游实际收到修改字节 |
| 10 | Correlation | HTTP Request → PID → TID → Java Stack → JNI → Native Stack → Module 形成 AnalysisObject |

## 15.2 Layer 2：语义验收（v1.1 新增）

**Hook：**

```text
runtime.hook → OK  ❌ 不够
必须：HOOK_INSTALLED + HOOK_ENTER + HOOK_LEAVE
且事件含：PID · TID · timestamp · arguments · backtrace
```

**Memory：**

```text
memory.write → OK  ❌ 不够
必须：READ original → WRITE new → READ back → COMPARE
最终 verified = true
```

**Network：**

```text
capture_start → OK  ❌ 不够
必须存在 actual traffic，才能标记 capture_verified
```

**HTTPS：** 严格保持五级状态，禁止"抓到了 HTTPS"就宣称"HTTPS 可以修改"。

**Correlation：**

```text
Network Request → Java/JNI → Native → Hook → Thread → Memory → Network Response
request_id → thread_id → hook_event → native_call → response
建立实际证据链才算 CORRELATION_VERIFIED
```

## 15.3 验收纪律

```text
验收链（任何改动后必跑）：
1. compileall / 语法检查
2. 工具目录回归（Core/Expert 分面是否对齐）
3. --health（全依赖健康检查）
4. --smoke --smoke-dry-run（冒烟，不落盘）
```

# 18. 实施路线

> 原则：**把风险前移**，用最便宜的交付物尽早暴露最贵的风险（架构错 / 协议错 / 阻塞 I/O）。

| 阶段 | 目标 | DoD（完成定义） |
|---|---|---|
| **M0 契约冻结** | 协议文档 + 全工具 schema + 黄金样例 | 协议评审通过；schema 与工具规格逐字段一致；样例可被两端测试引用 |
| **M1 工程初始化** | NDK/CMake 骨架 + 依赖版本锁定 + LICENSE 核对 | `libai_analyzer.so` 可编译、可推包、可被 Zygisk 加载 |
| **M2 Walking Skeleton** | Zygisk 自动注入 + IPC 打通（HELLO/READY/ping） | 启动目标 APK → Session 自动出现；断线重连可演示；协议单测覆盖收发 |
| **M3 Runtime 垂直切片** | Frida-Gum 真正嵌入 → 第一个 Native Hook 实测 | 真机产生 HOOK_ENTER/HOOK_LEAVE，含 PID/TID/参数/backtrace |
| **M4 Memory + Network** | Memory Write 实测 + Network Capture + HTTP Intercept | read-back verified；下游收到修改后的数据 |
| **M5 全量铺开** | 按"依赖 + 性价比"分批补齐工具 | 每批工具含四件套 + 分面注册；契约测试通过 |
| **M6 质量加固与发布** | 四类门禁全绿 + 真机全流程回归 | 流程验收 + 语义验收双层通过；文档与代码同步 |

**分批展开的排序依据（依赖 + 性价比）：**

```text
5.1 原语层（直接包装已有能力）→ 5.2 外迁与参数化
→ 5.3 拦截接线（intercept / modify / forward）→ 5.4 新建（语义查询 + 高层编排）
```

## 18.1 关键推进纪律🟠

```text
在投入 N 倍于骨架的代码量之前，先确认最小链路在真实环境成立。
"真实环境成立"的证据 = 真实后端的真实元数据返回（不是 mock 的）。
Walking Skeleton 跑不通就投 3000 行，后面全是空中楼阁。
```

> 单人开发严格串行：协议定稿 → 后端服务端 → 客户端对接+真机联调 → 再铺开工具。协议没冻结前并行写两端 = 两端都在猜对方接口，**是负收益**。

# 19. 工程纪律（来自 ④⑤ 两份经验文档）

## 19.1 分层架构

```text
L6 门面层    ai_analyzer/host/server.py（MCPServer 实例 + 装配，不写业务逻辑）
L5 注册层    ai_analyzer/tools/（specs 规格 + handlers 薄封装）
L4 能力层    ai_analyzer/host/runtime_bridge.py（按领域切，不按调用频次切）
L3 门禁层    validation/（只读校验 + 错误码 + 修复建议）
L2 集成层    integrations/（外部 CLI/DLL/引擎适配，隔离其接口变化）
L1 资源层    res/ 快照 · config.py · paths.py（路径安全）
```

> 🔴 门面层不能堆成上帝文件；兼容 shim 只允许 `import` 转发，**一行逻辑都不许有**，且只减不增。

## 19.2 注册三件套（新工具静默不暴露的头号根因）

新工具必须同时改三处：

```text
1. tools/__init__.py 的 REGISTERED_TOOL_MODULES   （模块被加载）
2. server 的 _LAZY_IMPORTS                        （payload 可懒加载）
3. surfaces/ 的可见集                             （分面可见）
```

外加：客户端实际 list 到该工具（光看服务端日志不算数）。

## 19.3 阻塞 I/O 必须隔离🔴

```python
# ✅ 阻塞 I/O 丢线程池
result = await asyncio.to_thread(bridge.call, command)

# ❌ 直接同步调用 → 卡死事件循环 → progress/cancel/其他工具全部停摆
result = bridge.call(command)
```

心跳接收与重连逻辑放独立后台线程，与命令调用解耦。

## 19.4 无状态优先🔴

Session 是本项目唯一允许的有状态对象，且已配看门狗（§9.3）。除此之外：

```text
凡是"打开→操作→关闭"的三段式，优先设计成一段式原子工具
必须分段的，给每个状态设 TTL
查询类工具返回里带活动状态，让 AI 能自我发现泄漏
```

## 19.5 防"假成功"🟠

```text
判断"解析/转换是否正确"，不要问"能不能跑完"，要问"产物里有没有真实内容"
```

手段：内容合理性断言 / 独立路径交叉验证 / 状态分布自检 / 黄金样本回归 / 可重入自检。

## 19.6 文档先行🔴

```text
任何一端改动，必须先改文档再改代码
协议改动 → 先改 protocol.md → 两端跟进 → 契约测试验证
事故处理 → 先写修正手册（现象+根因+修复+为什么）→ 改代码 → 规则回写文档
```

只改代码不改文档的 PR 一律打回。文档里的常量在代码中定义为单一常量源，文档引用常量名而非重复数值。

## 19.7 失败样本同样归档🟠

失败产物（乱码的 dump、不完整的抓包）保留并标注失败原因 + 失败决策树。**删掉失败样本 = 下次重踩同一个坑。**

## 19.8 静态数据快照

工具行为依赖的外部知识（内置 API 索引、模板注册表）冻结成 `res/*.json` 入库，**运行期不去源仓库拉数据**。

# 21. 变更边界【冻结】

**以下内容不得再次变更**（除非发现 P0 架构缺陷）：

> **落地补正（2026-09-19）**：PC 侧包名由 `mcp/` 改为 `ai_analyzer/`。
