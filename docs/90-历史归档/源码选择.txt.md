对。**源码也必须跟着新架构重新锁定，不能继续沿用昨天那张源码表。**

我刚核了一遍当前仓库状态，有一个非常重要的变化：

> **`zygisk-module-sample` 已于 2026-08-04 被官方归档。**
> 但官方 README 明确说明：这是因为它本身就是只读模板，并不代表废弃；Zygisk API 的最新公开头文件仍然在这个仓库里，而且 API 向后兼容。([GitHub][1])

同时，Frida 当前最新正式版本已经是 **17.18.0（2026-09-09）**，Frida-Gum 也对应 17.18.0。([GitHub][2])

所以我们应该把源码供应链升级成下面这个版本。

### 但有一个架构上的关键调整

之前我们写的是：

```text
zygisk-module-sample
        ↓
直接改成我们的项目
```

现在我建议改成：

```text
zygisk-module-sample
        │
        ├── zygisk.hpp
        ├── API 参考
        └── 构建模板
                ↓
        我们自己的 Zygisk Host
                ↓
        Runtime Bootstrap
                ↓
        ┌─────────────────┐
        │ Runtime Plane   │
        │                 │
        │ Frida-Gum       │
        │ LSPlant         │
        │ Memory          │
        │ Module          │
        │ Thread          │
        └─────────────────┘
```

也就是说，**不应该把整个 sample 当成我们产品源码的长期上游依赖**。

官方 README 本身也明确说可以直接 clone/template 使用，并且 Zygisk API 最新公开头文件就是 `module/jni/zygisk.hpp`。([GitHub][1])

### Frida 也要从旧版本升级

之前文档里的：

```text
Frida 17.x
```

现在直接冻结：

```text
Frida / Frida-Gum
17.18.0
```

官方 Release 当前就是 17.18.0。([GitHub][2])

而且这次不是单纯升级数字。17.18.0 的 Gum 还加入了让 embedder 向 GumJS 暴露 native API 的机制，这对我们这种**把 Gum 静态嵌入自己 Runtime** 的架构尤其值得关注。([GitHub][2])

### LSPlant 要单独注意

LSPlant 仍然可以作为我们的 ART Backend，但不能简单写成“万能 Android Hook”。

当前仓库仍然有 Android 旧版本兼容问题的公开 issue，例如 Android 8.x 的 ART Hook 崩溃问题在 2026-08 仍有记录。([GitHub][4])

所以最终架构应该是：

```text
Runtime Engine
│
├── Native Backend
│      └── Frida-Gum 17.18.0
│
└── Java/ART Backend
       └── LSPlant
```

而不是让 LSPlant 负责整个 Runtime。

```text
01 哪些源码直接下载
02 哪些源码直接集成
03 哪些只做参考
04 每个仓库 GitHub 官方地址
05 当前最新 Release / Commit
06 Android/ARM64 是否支持
07 License
08 我们放到项目哪个目录
09 谁依赖谁
10 哪些源码必须自己维护 Fork
11 哪些源码不能直接集成
12 最终完整目录树
13 第一阶段实际下载清单
14 第二阶段实际下载清单
```

这样就不会再出现**“架构已经升级了，但源码表还是上一代”**的问题。
