# MCP 通用技术经验开发文档 2

> **定位**：一份**与具体业务无关**的 MCP 服务端开发经验手册。
> 它不教你"怎么 dump UE4"，而是回答一个更普适的问题——
> **"怎么把一个能跑的能力，包装成 AI Agent 真正用得好、用不崩、不烧 token 的 MCP 服务"**。
>
> **经验来源**：本项目（`ue4ImGuiAutoWorkingMcpBytear`）从 0 到真机可用的完整开发过程。
> 本项目是一个"手机上的 UE4 内存分析器 → MCP 服务器"的改造，恰好踩遍了 MCP 开发几乎全部的坑：
> 跨语言两端（C++ ↔ Python）、阻塞 I/O、长任务、危险操作（内存写/远程调用）、断线重连、
> 大文件传输、AI 幻觉、token 爆炸、有状态泄漏……
> **所以本项目踩过的每一个坑，都是未来任何 MCP 项目的预演。**
>
> **怎么用本文**：
> - 第 1–3 章是**世界观**——先转变"MCP 是给人调 API"的旧观念，否则后面全是返工。
> - 第 4–13 章是**设计决策**——每条都给出"规则 + 为什么 + 违反会怎样 + 代码级怎么做"。
> - 第 14–16 章是**工程与流程**——怎么把上面这些落成可验证的交付。
> - 第 17–19 章是**验收**——怎么判定"做好了"。
> - 第 20 章是**附录**——可直接抄的骨架代码与速查表。
>
> **阅读约定**：🔴 = 违反会出线上事故级问题；🟠 = 会显著劣化体验/成本；🟡 = 规范性，迟早要补。

## §1 核心认知：MCP 是"给 AI 的接口"，不是"给人调的 API"

> 这是整份文档的地基。**90% 的 MCP 返工，都源于用"给人用"的思维设计工具。**

传统 API 的设计对象是人（或另一个已知行为的程序）：调用者会读文档、会重试、会看 HTTP 状态码、
会自己判断"这个返回是不是对的"。**但 MCP 的调用者是 LLM——一个会忘、会猜、会烧钱、会重试到死的"客户"。**
给 AI 设计接口，和给人设计接口，至少有 **7 个根本差异**：

### 1.1 AI 的 7 个"特性"（全是缺陷，必须用设计去对冲）

| # | AI 特性 | 后果 | 设计对策（后文展开） |
|---|---|---|---|
| 1 | **按 token 计费，上下文有限** | 返回一大段 = 烧钱 + 挤掉后续推理空间 | §3 Token 预算：单响应 ≤4K token、分页、`brief` 摘要 |
| 2 | **会"失忆"** | 多轮后忘了之前扫描过的候选、忘了已验证的地址 | §8 结论落盘 + 返回带可追溯标识 |
| 3 | **会"胡编"** | 没拿到证据就敢下结论（"最可能的地址是 X"） | §8 证据内嵌：强制把样本/评分塞进返回值 |
| 4 | **会"重试风暴"** | 工具没返回 / 慢 → AI 盲目重试 → 并发爆炸 | §6 长任务五件套 + 耗时档位标注 |
| 5 | **被负向表述强烈带偏** | 工具说 "not found" → AI 放弃或乱猜，忽略后面有用的信息 | §4 禁止 "not found"，返回次优候选 + 中性描述 |
| 6 | **分不清"调错"和"后端失败"** | 参数传错它不修，后端报错它却重试 | §7 错误分层：JSON-RPC error vs `isError:true` |
| 7 | **会漏调"收尾动作"** | 有状态工具漏调 `end`/`release` → 资源永久泄漏、目标冻结 | §5 无状态优先 + 兜底看门狗 |

### 1.2 由此推出的 3 条设计总纲

1. **判定权永远在 AI，工具只给"原始观测值 + 中性描述"。**
   工具不要替 AI 下结论（"无效""不存在"），要给够数据让 AI 自己判。
   反例：`sampleGNames` 解出乱码就替 AI 判"无效"——AI 需要看到那串乱码原文才能推理。

2. **AI 的每一步"下一步该调什么"，必须由工具返回里显式告诉它。**
   人靠文档，AI 靠 `instructions` + 每个工具 `description` 里的 `<important_notes>`（"前置条件 / 易错点 / 下一步调什么"）。
   详见 §4.3。

3. **默认只读，写/危险操作显式确认 + 兜底。**
   AI 会传错地址，传错地址在你的工具里可能就是"写崩目标进程"。详见 §9。

### 1.3 一个反直觉的结论

> **"工具越少、返回越胖"往往比"工具多、返回瘦"更烧 token、更难用。**
> 每个工具的 `description` + `inputSchema` + `outputSchema` + `annotations` 都是**常驻上下文**。
> 43 个工具全量常驻 ≈ 25–35K token，还没开始干活上下文就吃了 1/4。
> 所以：**高层"正门"工具做主入口，原语做兜底，不需要的组动态挂载。**（§4.6）

## §2 契约先行：两端（或多端）之间先冻结合乎 AI 特性的协议

> 🔴 **跨进程 / 跨语言的 MCP，协议是第一资产。** 两端（客户端服务 + 后端执行体）是独立二进制，
> 任何一端改动都必须**先改协议文档再改代码**，否则就是静默不兼容。

### 2.1 为什么"契约先行"在 MCP 里比一般 API 更重要

普通 REST API 有 HTTP 语义兜底（状态码、Content-Type、标准错误结构），两端"约定俗成"就能跑。
MCP 后端经常是**自研协议**（socket / gRPC / 私有 TCP 帧），**没有任何兜底**——
帧格式、握手、错误码、长任务语义、断线语义，**全部要你自己定死**。

本项目就是一个跨语言两端：
```
PC 侧（Python / FastMCP）  ──TCP+NDJSON, 127.0.0.1:35515──  设备端（C++ / nlohmann/json）
   客户端（发起请求）                                            服务端（bind+listen+accept）
```
两端独立编译、独立发版。如果协议没先冻结，就会出现：
- 设备端改了帧格式，PC 侧解析全错，但**没有任何一方报错**（静默不兼容）；
- 长任务返回格式两边理解不一致，AI 以为"失败了"其实"还在跑"。

### 2.2 一份合格的 wire protocol 必须写死这 8 件事

| # | 必须定义 | 本项目实例 | 不写死的后果 |
|---|---|---|---|
| 1 | **传输与绑定** | TCP，设备端 `bind("127.0.0.1",35515)`，仅经 adb forward | §9 安全漏洞 |
| 2 | **帧格式** | NDJSON（换行分隔 JSON），弃用手写 `OK <len>\n<body>` | 手写解析 = 安全/兼容问题根因 |
| 3 | **握手与版本协商** | 设备端主动发 `HELLO{protocol,build,capabilities}`，PC 校验 `protocol` 不匹配即报错断开 | 换版后静默不兼容 |
| 4 | **请求 / 成功响应 / 失败响应** | `{id,cmd,args}` → `{id,ok:true,data}` / `{id,ok:false,error:{code,msg}}` | 两端理解不一致 |
| 5 | **长任务语义** | 未完成返 `{jobId,status,progress,etaSeconds,suggestedWaitMs}` | AI 盲目重试（§6） |
| 6 | **错误码表 + 分层** | 协议错 vs 执行错（§7） | AI 分不清调错还是后端失败 |
| 7 | **心跳与超时** | 每 2s 心跳帧；单命令硬超时 120s | AI 分不清"在算"还是"死了"（§6） |
| 8 | **断线重连 + 会话失效** | 指数退避 1/2/4…≤30s，重连必重新 HELLO，**所有 sessionId 立即失效** | 重连后拿着失效 session 继续操作（§10） |

### 2.3 版本协商是"免费保险"

两端是两个二进制，**换版是常态**。只要握手时交换 `protocol` 版本号，
不匹配就**明确报错**（而不是让后续每条命令都失败），排障成本从"小时级"降到"秒级"。
> 经验：本项目把 `HELLO.protocol` 不匹配定为最高优先级错误 `E_PROTOCOL_MISMATCH`，
> PC 侧一收到就 `close()` 并明确告诉 AI"设备端与客户端协议版本不匹配，需升级"。

### 2.4 命令分级要写进协议

协议里必须明确哪些命令是"快"（毫秒级）、哪些是"重活"（秒~分钟级），
因为**后端线程模型、客户端超时策略、AI 的 `waitMs` 选择**全都依赖这个分级。
（§6 与 §12 会展开为什么。）

### 2.5 反模式：把"应用层逻辑"塞进协议

协议只负责**传输 + 语义对齐**，不承载业务逻辑。
本项目曾考虑让设备端直接实现"一键定位引擎全局"的多步编排，
最终决定**把编排放在 PC 侧**——因为设备端改一次要重编译+推包+重启（迭代慢两个数量级），
而协议层（原子命令）保持稳定，编排层（PC 侧 Python）快速迭代。
> **原则：把"变化快的逻辑"放在迭代快的一端，把"稳定的原子能力"放在协议里。**

## §3 Token 预算：把"上下文成本"当作一等公民

> 🔴 **MCP 的"性能指标"不是 QPS，是 token。**
> 每一次工具调用 = 一段 description/schema 常驻成本 + 一次响应成本。
> 不做预算控制，AI 会在 3–5 轮之后开始"忘事"、"乱猜"、"重复调用"。

### 3.1 三个层次的 token 成本

| 层次 | 内容 | 成本模型 |
|---|---|---|
| **常驻** | 每个工具的 `name` + `description` + `inputSchema` + `outputSchema` + `annotations` | 每次会话初始化后**一直占着**上下文。`outputSchema` 常被漏算：每个 200–500 token × 工具数 |
| **调用** | AI 发出 tool call 的参数 JSON | 小，但 AI 会重试 → 重复花 |
| **响应** | 工具返回的 `structuredContent` + 文本 | **最容易被低估**：一个 64KB 的 hex dump ≈ 13 万字符 ≈ 33K token，一次响应打爆上下文 |

### 3.2 四条硬规则（本项目实战数值，可直接抄）

1. 🔴 **单工具响应 ≤ 4K token**（违反视为 bug）。
   落地手段：
   - 二进制/大块数据**限制单次大小**（如内存读 size 上限 4096 字节，而不是 65536）；
   - 超限**必须分页**，返回 `nextCursor`，AI 翻页而不是"一次拉全"；
   - 日志类默认 `maxLines=50`，环形缓冲上限写死（如 1500 行）；
   - 候选/列表类默认 `maxCandidates=50`，上限 2000。
2. 🔴 **常驻工具数 ≤ 25（上限 45）**。
   核心组常驻；低频/危险组（如 ptrace 远程调用、重型反汇编）靠 `tools.listChanged` **动态挂载**——
   后端能力不可用（如权限被拒）时**主动摘除**并通知客户端，而不是等 AI 调了才报错。
   每新增一个工具，PR 里必须写明"增加了多少常驻 token + 是否常驻"。
3. 🟠 **列表类工具统一支持 `brief` 参数**（响应分级）：
   - `brief:true` → 只回统计 + 前 N 条摘要（<200 token），AI 先看全貌；
   - `brief:false` → 完整列表（仍受上限 + 分页约束），AI 再用 `cursor` 取细节。
   把"一次吃全"变成"先看后取"。
4. 🟡 **描述瘦身**：`<important_notes>` ≤ 5 条、description 总量 ≤150 token；
   能用 `use_case` 一句话说清的，不写长段。术语保留英文原文（AI 认的是原文，翻译反而降低命中率）。

### 3.3 轮询的 token 成本常被忽略

每轮空轮询 ≈ 100–200 token，30 轮 ≈ 6K，**白烧**。对策（与 §6 联动）：
- 轮询响应必带 `progress` + `etaSeconds` + `suggestedWaitMs`，AI 按建议等待；
- 支持**长轮询**：后端在 `waitMs` 窗口内 hold 连接，把 N 次空轮询压成 1 次带结果的返回。

### 3.4 大文件：token 问题的"越界"解法

> 🔴 **几十 MB 的产物文件绝不做 MCP resource、绝不塞进协议响应。**
> 客户端可能把它整个读进上下文，直接爆炸。

正确做法是**双通道**（§11 详述）：
- 产物落盘在后端本地目录（如 `/sdcard/...` 或服务器磁盘）；
- 协议里只传**元数据**（路径、大小、hash、mtime）；
- 读取走**服务端过滤**（"给我 X 类的那一段"）或独立传输通道（`adb pull` / `scp` / 下载链接）。

### 3.5 结论要"落盘"，不要"存对话"

AI 的判定结论（"GNames 在 0x...，证据是前 16 个名称"）如果只存在对话里，
新会话全重来——**既烧 token，又可能给出漂移的结论**。
规范：验证通过的结论 + 证据写入约定文件（如 `<output_root>/<target>/mcp_analysis.json`），
新会话**先读它再决定是否重做**。未落盘的结论视为临时、不可信。
（这一条在 §8 与 §17 还会再出现——它是"防失忆 + 防漂移 + 省 token"三合一。）

## §4 工具设计的 8 条硬规范

> 每一条都来自真实事故或真实浪费。第 1、2、5、8 条违反时**线上直接出事故或 AI 直接翻车**。

### 4.1 命名：camelCase + 动词开头 + 语义唯一 🔴

- `readMemory` / `scanPattern` / `listProcesses`——GPT 系分词下 camelCase 比 snake_case 省 token
  （`memoryRead` ≈ 2 token vs `memory_read` ≈ 3 token）。
- **动词开头**，让 AI 一眼看出"做什么"：`scan...` / `sample...` / `get...` / `start...`。
- **一个工具只做一件事**，名字能无歧义表达它。重名/近名（`scanA` 与 `scanCandidates`）必须在
  description 里写清分工，否则 AI 会随机选。
- 注意：**MCP 工具名（camelCase）与后端原生命令名（大写下划线）是两层，不要混**
  （本项目：工具 `readMemory` ↔ 命令 `MEMORY_READ`）。

### 4.2 每个工具必须有完整的"四件套" 🔴

```
name/title/description + inputSchema + outputSchema + annotations
```

| 件 | 要求 |
|---|---|
| `description` | 必须含 `<use_case>`（什么时候该调它）+ `<important_notes>`（前置条件 / 易错点 / **下一步该调什么**）+ 中文同义触发词（"找函数 / 定位特征码 / 搜 pattern"都指向 `scanPattern`）+ **耗时档位**（快 <1s / 中 <30s / 慢 <5min） |
| `inputSchema` | 每个可选参数**必须有 default**；数值标 `minimum/maximum`；数组标 `maxItems`；十六进制串用 `pattern` + 实现里查偶数长度；`additionalProperties: false` |
| `outputSchema` | **每个有返回数据的工具必须声明**，且与 `structuredContent` 严格一致（写单测反向校验）；地址用字符串 `"0x..."` 不用 number（防精度丢失与进制歧义）；数组必带 `maxItems` |
| `annotations` | `readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint` 全部显式给出——客户端靠它**自动放行只读工具**，缺了它用户每次读内存都要点确认 |

> 为什么 outputSchema 重要：没有契约，`structuredContent` 就是无 schema 的自由格式，
> AI 解析容易出错，而且每次返回结构漂移一次，AI 的理解就偏一次。

### 4.3 禁止 "not found" 响应 🟠

> 出处：LLM 最佳实践——"LLMs can be overly influenced by negative statements like
> 'not found', causing them to ignore the useful information that follows."

| 场景 | ❌ 禁止 | ✅ 正确 |
|---|---|---|
| 扫描零命中 | `"未找到 GNames"` | 返回**放宽条件后的次优候选** + "严格条件下 0 命中；以下 5 个是放宽指针范围后的候选，锚点命中数较低，建议逐个验证" |
| 无精确匹配 | `"类 X 不存在"` | 返回模糊匹配的类名列表 |
| 符号不存在 | `"符号未找到"` | 返回名字相近的符号 + 提示"可能已 strip，可改用特征码搜索" |
| 解出乱码 | 替 AI 判"无效" | **原样返回字符串**，让 AI 自己看 |

原则：**工具给数据 + 中性描述，判定权永远在 AI。**（§1.2 总纲 1 的落地。）

### 4.4 分层"正门"：高层用例做入口，原语做兜底 🔴

不要给 AI 一堆平级原语让它自己拼——它会乱拼。设计三层：

```
┌─ 高层用例（正门）─────────┐  AI 首选，一次调用完成完整用例
│  locateXxx / doTask       │  （本项目：locateEngineGlobals / dumpSDK）
└───────────────────────────┘
            ↓ 失败或需细粒度控制
┌─ 复合操作 ─────────────────┐  一次调用顶 N 次原语，专门降轮次
│  followChain / scanAll     │  （本项目：followPointerChain / scanCandidates）
└───────────────────────────┘
            ↓ 仍不够
┌─ 原语 ─────────────────────┐  兜底，让 AI 能拼出未预置的策略
│  read / write / search …   │  （未知目标必然有高层覆盖不到的情况，原语不能删）
└───────────────────────────┘
```

配套三条：
1. **Server `instructions` 里写明"优先用高层工具"**，让 AI 默认走正门；
2. **复合操作是必做项**（直接对冲"轮次太多"）；
3. **原语不删**——与"已知 API 的系统"不同，逆向/未知目标场景高层必然覆盖不全。

> ⚠️ 编排放哪端？变化快的编排逻辑放**迭代快的一端**（本项目 PC 侧 Python），
> 设备/后端只提供稳定原子命令。改后端一次的成本（重编译/推包/重启）高两个数量级。（§2.5）

### 4.5 工具描述里写"下一步" 🟠

AI 的下一步质量 = 你的 description 质量。每个工具的 `<important_notes>` 最后一条
应该是"成功/失败后分别该调什么"。示例（本项目 `scanGNames`）：
```
<important_notes>
1. 先调 detectUEVersion 确认版本，可显著缩小搜索范围。
2. anchorNames 至少给 3 个内建锚点，单锚点误判率高。
3. 本工具只返回候选摘要，必须用 sampleGNames 取样本后才能判定。
4. 结果按 session 缓存，换判据重评无需重扫。
</important_notes>
```

### 4.6 工具总数与动态挂载 🟠

- **硬上限 45，常驻 ≤25**（§3.2 规则 2）；
- 动态挂载靠 `initialize` 声明 `capabilities.tools.listChanged: true`；
- 挂载条件要写清（"设备端不支持 ptrace 时 F 组摘除"），**摘除要通知客户端**；
- 每次新增工具的 PR 必须回答：增加了多少常驻 token？是否常驻？

### 4.7 缓存必须"可见" 🟡

换参数重评可能命中缓存——AI 若不知情，会误以为"又扫了一遍"。
规范：**缓存命中的响应必带 `cached: true` + 原始参数回显**，并提示"强制重扫传 `forceRefresh: true`"。
缓存键与失效条件要写进文档（本项目：候选集按 `sessionId`，切进程/超时 10 分钟失效；
类索引按 `pid + dump 版本`，重新 dump 失效）。

### 4.8 危险工具的"默认关闭" 🔴

所有**写操作 / 能执行任意代码的操作 / 能冻结目标的操作**：
- 默认不可用或默认拒绝；
- 需显式参数开启（本项目：`confirm_dangerous: true`，默认 false，为 false 时返回中性提示而非执行）；
- `annotations.destructiveHint: true` 显式标注；
- instructions 里写"调用前必须先验证过目标"（如远程调用前先 `scanPattern`/`disassemble` 验证函数地址）。

（安全细节见 §9。）

## §5 无状态优先：有状态工具是 AI 场景下的"泄漏源"

> 🔴 **本项目最严重的事故级设计缺陷**：`beginAttachSession` / `endAttachSession` 是有状态工具，
> AI 漏调 `end` 会让**目标游戏永久冻结**。MCP 工具应尽可能无状态。

### 5.1 为什么"有状态 + AI"特别危险

有状态工具的正确使用要求调用者**严格配对** begin/end（或 open/close、lock/unlock）。
人能做到，LLM **做不到**——它会：
- 中间出错就走了，没走到 `end`；
- 会话过长，中途被别的工具调用打断，忘了"手里还拿着一个 session"；
- 多步推理时把 session 状态"想当然"地认为还在/已关。

任何"忘了 end"的后果都是**资源泄漏**，在逆向工具里具体表现为：目标进程被 ptrace 挂起
（游戏冻住）、文件句柄泄漏、内存锁泄漏。

### 5.2 三条对策（按优先级）

1. 🔴 **能设计成无状态就别设计成有状态。**
   把"begin → N 次操作 → end"压缩成**一个原子工具**：
   ```
   callRemoteFunctionBatch(address, argSets[], returnKind)
   内部：attach → N 次调用 → detach
   外部：一次工具调用，无状态，不可能泄漏
   ```
   本项目 95% 的场景（批量取名字、批量验证候选）都被这一个无状态批处理工具覆盖了，
   原来 N 次有状态调用变 1 次，还顺便拿到了最优的"一次冻结做 N 件事"效率。

2. 🔴 **必须保留有状态工具时，上"四重兜底"，缺一不可：**
   | 兜底 | 机制 |
   |---|---|
   | ① 最长持有 | `maxHoldMs` 参数（默认 3000，上限 30000），服务端到点**强制**结束 |
   | ② 空闲看门狗 | 会话内超过 N 毫秒无操作，自动结束 |
   | ③ 异常兜底 | 任何工具异常 / 参数错误，**先结束会话再返回错误**（顺序不能反，否则异常也泄漏） |
   | ④ 断连兜底 | 客户端流关闭 / 进程退出，析构里强制结束 |
   另外要处理**目标消失**：被挂起的进程崩溃时，底层 attach 会返回 `ESRCH`，
   此时要**清理状态并正常返回**（不要抛异常，否则又会漏掉结束逻辑）。

3. 🟠 **让 AI 能"自我发现"泄漏。**
   查询类工具（如 `getCapabilities` / `ping`）的返回里带**活动会话状态**
   （`activeAttachSession: true/false`）。AI 看到泄漏能自己补救（显式 end 或重建会话）。

### 5.3 推而广之

"无状态优先"不只是针对 attach：
- 凡是"打开 → 操作 → 关闭"的三段式，优先设计成**一段式原子工具**；
- 必须分段的，给每个状态**设 TTL**，让"忘记关闭"的代价是"自动过期"而不是"永久泄漏"；
- 返回里暴露状态，让 AI 可观测、可补救。

## §6 长任务：异步、轮询、心跳、取消、超时，五件套缺一不可

> 🔴 **长任务处理是 MCP 最容易翻车的部分。**
> AI 面对一个"卡住"的工具调用，唯一本能就是重试——于是重试风暴，把后端打爆。
> 本项目把长任务拆成五件套，缺任何一件都会出问题。

### 6.1 五件套

| # | 件套 | 解决什么 | 本项目做法 |
|---|---|---|---|
| 1 | **短等优先（waitMs）** | 快速任务不必 2 次往返 | 工具带 `waitMs`（默认 5000，上限 60000）：窗口内完成直接返结果（1 次往返）；超时返 `{jobId,status,progress}` |
| 2 | **进度 + 建议等待** | AI 盲目短轮询烧 token | 轮询响应必带 `progress` / `etaSeconds` / `suggestedWaitMs`，AI 按建议等 |
| 3 | **长轮询（hold）** | N 次空轮询压成 1 次 | 后端在 `waitMs` 窗口内可 hold 连接不放，直到完成或窗口上限 |
| 4 | **心跳** | AI/PC 分不清"在算"和"死了" | 后端每 2s 发心跳帧（`{ts,busy,activeJobId}`），无论是否有请求在处理；PC 超 10s 无心跳判假死 |
| 5 | **取消 + 硬超时** | 任务可能永远不结束 | `cancelJob(jobId)` 协作式取消（worker 循环里检查取消点）；单命令硬超时 120s，超时回 `E_TIMEOUT` + 当前 progress，**绝不无限执行** |

### 6.2 为什么"心跳"是防卡死的命门

没有心跳时，PC 侧面对一个不返回的工具调用只有两种理解："还在算"或"挂了"，**无法区分**，
只能盲等 → 超时 → 重试 → 又盲等。有心跳后：
- 心跳正常 + `busy=true` → "在算"，安心等 `suggestedWaitMs`；
- 心跳正常 + `busy=false` → 后端空闲但我的请求没回 → 后端内部 bug，可诊断；
- 心跳消失（>10s） → "死了"，立即断开重连（重连后该 job 作废，语义 `E_CANCELLED`）。

### 6.3 为什么"硬超时"是命门

> 绝不允许命令无限执行——这是"工具调用卡死"的根因。

协作式取消点要埋在 worker 的循环里（本项目在 `DumpUiState` 里加 `cancelRequested` 标志，
worker 每轮检查）。硬超时与取消是两回事：取消是"用户/AI 主动"，超时是"后端自保"。
超时后返回 `E_TIMEOUT` + 已有 progress，**PC 侧把它当作"后端可能异常"的信号去探活**，
而不是直接当作"任务失败"。

### 6.4 耗时档位标注（工具设计层）

🔴 **每个工具描述必须标预期耗时档位**：`快 <1s` / `中 <30s` / `慢 <5min`。
原因：AI 只有知道这是个"慢"工具，才会：
- 选大的 `waitMs`（而不是默认 5s 就超时去轮询）；
- 不触发重试风暴（"这么慢是正常"）。
不知道档位时，AI 一律按"应该很快"的预期对待，慢工具 = 慢工具被当成卡死。

### 6.5 命令分级是五件套的前置

后端线程模型决定了长任务"怎么跑"（§12 详述）：
**快命令在命令线程直接执行，重活投 worker 线程**——否则分钟级重活会把
`ping` / `getLogs` / `getProbeStatus` 全部堵住，AI 误判掉线，反而触发更多重试。
分级表要写进协议文档（§2.2 第 8 条）。

## §7 错误分层：让 AI 分清"我调错了"和"后端失败了"

> 🟠 **协议层错误与执行层失败必须二分，混为一谈 = AI 无法自我纠错。**

### 7.1 两层的定义与返回方式

| 类型 | 含义 | 例子 | 返回方式 |
|---|---|---|---|
| **协议层错误** | 客户端（AI）调错了 | 未知工具名、参数 schema 校验失败、JSON 解析失败、协议版本不匹配 | **JSON-RPC `error`** |
| **执行层失败** | 调用本身合法，但后端执行时失败 | 读内存失败、扫描无结果、权限被拒、目标进程已退出 | **`isError: true` 的 tool result** |

为什么必须分：
- 协议层错误 → AI 应该**改参数**（它传错了）；
- 执行层失败 → AI 应该**换策略 / 看日志 / 换候选**（后端的事）。
混在一起时，AI 分不清自己该干嘛，行为不可预测。

### 7.2 错误码要"可行动"

每个错误码应该能直接指导 AI 的下一步（本项目错误码表节选）：

| 错误码 | 含义 | AI 应该做什么 |
|---|---|---|
| `E_PROTOCOL_MISMATCH` | 协议版本不匹配 | 停止，报告需升级（不可重试） |
| `E_BAD_ARGS` | 参数错 | 改参数 |
| `E_READ_FAILED` | 读内存失败 | 检查地址 / 换候选 |
| `E_PROBE_FAILED` | 探测失败（附状态枚举字符串） | 看 `getLogs` 找具体原因 |
| `E_NOT_READY` | 前置条件未满足（probe 未完成 / 进程已切换） | 先做前置步骤 |
| `E_TIMEOUT` | 后端硬超时 | 当作"后端可能异常"，探活 |
| `E_CANCELLED` | 被取消 | 重新发起 |
| `E_MAP_STALE` | 绑定的映射版本已变化 | 重新 `listModules` / 重扫 |
| `E_SESSION_STALE` | 候选 session 已过期 / 进程已切换 | 重新生成候选 |
| `E_PTRACE_FAILED` | 远程调用失败（含不可用/权限/进程退出） | 降级或不执行 |
| `E_NOT_FOUND` | 符号/资源未找到 | 换搜索方式（如改特征码） |

### 7.3 详细错误是功能，不是风险 🟡

> 常见误区：为了"不泄露内部信息"把错误消息写得很笼统（"操作失败"）。
> **对本地单用户调试工具，这是错的。** 详细错误（含地址、错误码、状态枚举字符串）
> 是 AI 决定下一步的核心输入——它要靠错误消息判断"换什么参数、看哪个日志"。
> 只有当你把工具暴露给不可信客户端时，才需要重新评估"描述性错误"的风险。
> 本项目明确记录了这一"有理由的偏离"：详细错误是**核心功能而非风险**。

### 7.4 错误消息里附"诊断钩子"

执行层失败时，返回里尽量附带**下一步诊断入口**：
- `E_PROBE_FAILED` 附带可读的状态字符串（`ERROR_INIT_GUOBJECTARRAY`）；
- 任何失败都提示"看 `getLogs`"——设备端日志通常直接指出原因；
- 附带 `suggestedNextAction`（可选字段）直接告诉 AI 下一步。

## §8 防幻觉设计：把证据内嵌进返回值，判定权留给 AI

> 🔴 **本项目 v1.2 审查的第三大事故级问题：AI 判定没有证据内嵌，会"跳过采样直接猜最像的"。**
> 防幻觉不是"让 AI 变聪明"，而是**让 AI 想跳过证据都跳不过去**。

### 8.1 幻觉的典型形态（本项目实测）

原始流程是三轮往返：`scanXxx` 返回地址列表 → AI 挑一个"最像的" → 再调 `sampleXxx` 验证。
问题：
1. **AI 经常跳过第 3 步**，直接对"最像的地址"下结论——而"最像"是它凭地址数值猜的；
2. 三轮往返烧 token，且每轮之间 AI 的"记忆"在漂移；
3. 返回的"命中数较低"被 AI 理解成"不是"，直接弃用——而真相可能是"参数太严，放宽就有"。

### 8.2 对策一：证据内嵌，"扫描-采样-判定"三轮压一轮 🔴

**扫描类工具的每个候选，直接内嵌"前 N 个样本 + 评分"一起返回**：
```
scanGNames 返回：
candidates: [
  { address: "0x...", anchorHits: 5,
    samples: ["None", "ByteProperty", "IntProperty"],   ← 证据直接在场
    engineNameHits: 5 }
]
```
效果：
- AI 想跳过采样都跳不过去——证据就在返回值里；
- **判定结论必须引用具体样本字符串**（写进 instructions：禁止只报"最可能的地址"）；
- 一轮调用完成原来三轮的"扫描→采样→判定"。

> 泛化：**凡是"先找候选、再验证候选"的工具族，把验证证据内嵌进候选返回**，
> 不要做成"返回地址，AI 自己去验证"。

### 8.3 对策二：原始观测值原样返回，不替 AI 下结论 🔴

- 解出乱码？**原样返回那串乱码**，不要替 AI 判"无效"。
  AI 需要看到乱码的形态（半词？函数后缀？替换字符？）才能推理出"这是静态字符串表不是名字池"。
  本项目乱码排查决策树（"名称是半词/函数后缀？检查候选是否落入静态 ASCII"）就是
  **AI 基于原样返回的乱码文本**做出的判断。
- "命中数较低" ≠ "不是"。instructions 里明写：
  **"工具返回的都是原始观测值，判断权在你。工具说'命中数较低'不等于'不是'。"**

### 8.4 对策三：判定结论落盘 + 引用 🟠

- 验证通过的结论 + 证据写入约定文件（`mcp_analysis.json`），
  **新会话/重连后先读它**，避免重做整轮扫描和判定（省 token + 防结果漂移）；
- 未落盘的结论视为**临时、不可信**（写进 instructions）；
- 结论里必须包含"证据引用"（样本字符串、地址、日志行），让下一个会话能**复核**而不是盲信。

### 8.5 对策四：instructions 是"防幻觉总闸" 🟠

Server `instructions` 里必须固化：
1. **首选工作流的固定顺序**（顺序不可颠倒，每步的"为什么"写清楚）；
2. **判定黄金法则**（"名字表对不对，看前 16 个字符串：开头必然是 None/ByteProperty/IntProperty/…"——
   用**所有目标都成立的不变量**做判据，比让 AI 自由发挥可靠得多）；
3. **硬性约束清单**（"永远用 sample 取样本后自己判断，不要凭地址猜测"）；
4. **易错点清单**（"不要假设偏移——偏移来自 dump 的真实数据，不是推理出来的"）。

> 经验：**"不变量判据"是防幻觉的核武器。** 给 AI 一个"在所有合法目标上都必然成立的特征"
> （UE 游戏 FName 表前 16 项必然是引擎内建名），比给一堆"建议"有效 10 倍。
> 每个领域项目都应该先整理出自己的"不变量清单"（本项目见 `docs/SDK分析判定规则.md`）。

### 8.6 对策五：可复现性 🟡

- 搜索/候选类响应携带 `mapRevision` / `sessionId` / 进程启动时间等**快照标识**；
- 跨调用引用同一快照（应用 override 时 revision 不匹配 → `E_MAP_STALE`），
  防止 AI 拿着"几分钟前的绝对地址"往"已经变化的进程"上打；
- 重要结论附"可重放参数"（当时的 Base + 相对偏移 + 候选 + 原始内存片段哈希），
  支持离线复核。

## §9 安全基线：默认只读、危险显式确认、最小暴露面

> 🔴 **本项目 v1.2 审查发现的第四大问题：socket 未规定 bind 地址。**
> root 权限 + 无认证 + 内存写接口，若 bind 0.0.0.0 = **局域网任意设备可读写目标游戏内存**。
> 安全设计不是"加个密码"，而是**从暴露面、默认值、确认机制三个层面同时设防**。

### 9.1 暴露面：最小化 🔴

| 规则 | 说明 |
|---|---|
| **默认只监听回环** | 设备端/后端强制 `bind("127.0.0.1", port)`，绝不 `0.0.0.0` / `INADDR_ANY`；仅经 `adb forward`（或等价隧道）暴露 |
| **非回环必须显式配置** | 需要局域网/远程时，必须写一个**显式配置文件**（本项目 `/sdcard/UnrealMemoryTools/mcp_bind.conf`），且**用完即删配置并重启**——让"暴露"成为一个有意识、可审计、会过期的动作，而不是默认状态 |
| **全局暴露 = 危险档** | `0.0.0.0`（蜂窝网可达）单独列为"危险"模式，文档标红 |
| **单对单是设计前提** | 本项目明确"一个客户端 ↔ 一个服务端，并发恒为 1"，因此严格串行协议是**最优解而非折中**——不要为不存在的并发加连接池/reqId（过度设计也是风险源） |

### 9.2 默认只读，写操作显式开启 🔴

- **所有工具默认只读**；写操作（内存写、配置修改）默认关闭，需显式参数开启；
- **写前校验**：`writeMemory` 收到地址后，**先校验目标映射**——
  地址落在已映射区间内 + 区间权限包含 `PROT_WRITE`；越界或不可写 → **拒绝执行并返回中性说明**，
  而不是"试试看能不能写"。本项目直接复用已有校验器（`KittyPtrValidator`）——
  **写路径的校验器必须独立于读路径**，读失败≠写安全；
- **可撤销**：写操作支持 `MemoryBackup`（写前备份，支持撤销）。

### 9.3 危险操作：显式确认 + 前置验证 🔴

**能力最强 = 最危险**的工具（能在目标进程执行任意地址的任意函数）：
1. 参数 `confirm_dangerous: boolean`，**默认 false**；为 false 时**返回中性提示而非执行**
   （"需要显式确认才能执行"——AI 读到提示会补上参数重新调用，这是合法的自我确认流程）；
2. **前置验证写入 instructions**：调用前必须已通过特征码搜索/反汇编验证过函数地址，
   "先验证再调用"是流程约束，不是建议；
3. `annotations.destructiveHint: true`，让客户端在 UI 层也弹确认（双保险）；
4. 危险工具组（F 组 ptrace）默认**动态挂载**——后端能力不可用/用户未启用时整组摘除（§3.2）。

### 9.4 认证的设计取舍 🟠

- 单对单本地调试场景：`HELLO` 握手后**无需 Token** 直接调用（暴露面已锁死在回环 + adb forward，
  加 Token 是形式主义）；
- **但协议要预留认证位**：HELLO 里带 capabilities，未来加 `AUTH` 帧不需要改协议主干；
- 一旦工具暴露到不可信网络（非回环 + 公网）：**必须加认证 + TLS**，且重新评估"详细错误消息"
  是否泄露内部路径（§7.3 的取舍要反转）。

### 9.5 安全红线清单（可直接抄进你的项目）

- 🔴 bind 只许回环（除非显式配置，且配置有审计痕迹、会过期）；
- 🔴 写前必校验映射权限；
- 🔴 任意代码执行类工具必 `confirm_dangerous`；
- 🔴 日志里不打印密钥/token（本项目约定提交前检查 `*.pem` 未误提交）；
- 🟠 危险操作走 backup/可撤销；
- 🟠 暴露到不可信网络前，重审"详细错误"与"无认证"两条取舍。

## §10 断线重连与"会话失效"语义

> 🔴 **USB 拔插 / adb 掉线 / 后端进程被杀，是高频故障，不是边缘情况。**
> 架构只处理"后端崩溃"是不够的——**重连的语义**必须像协议一样写死。

### 10.1 重连三原则

1. **指数退避重连**：1s / 2s / 4s / … 上限 30s（上限防止"疯狂重连"占满事件循环/端口）；
2. **重连成功必重新握手**：重新 `HELLO` + 校验 `protocol` + 重新拉取 `capabilities`
   （后端可能换了版本/能力集）；
3. **重连期间 in-flight 调用明确失败**：返回 `isError: true` + 明确文案
   （"连接已断开，已自动重连，请重试"）——**不要静默吞掉**，AI 需要知道"刚才那步没执行"。

### 10.2 会话失效语义 🔴

> **重连后所有 `sessionId` 立即失效**（扫描候选集、类索引、job 全部作废），AI 必须重建。

为什么这么狠：
- 后端重启后，旧 session 数据**不恢复**（这是预期行为，文档写明）；
- 若允许"重连后继续用旧 sessionId"，AI 会拿着一份**可能不存在**的候选集继续操作，
  后续每一步都建立在幽灵数据上；
- "全部失效 + 强制重建"虽然多花几轮调用，但**状态永远自洽**——
  对 AI 来说，"多花 3 轮"远好于"在幽灵数据上推 10 轮然后全错"。

### 10.3 判活与重连的联动（与 §6.4 心跳联动）

| 观测 | 判定 | 动作 |
|---|---|---|
| 心跳正常 + `busy=true` | 在算 | 按 `suggestedWaitMs` 等 |
| 心跳正常 + 请求无响应 | 后端内部异常 | 记日志，必要时 `cancelJob` 后重建 |
| 心跳消失 > 10s | 假死/断线 | 断开 → 指数退避重连 → 重新 HELLO → 旧 job 作废（`E_CANCELLED` 语义） |
| 重连成功 | 新会话 | 所有 sessionId 失效，AI 从"重连后先做什么"的固定流程恢复 |

### 10.4 "重连后先做什么"要写进 instructions 🟠

AI 重连后的第一步不应该是"重试刚才失败的调用"，而是**重建上下文**：
```
ping（确认连接+版本）
→ listProcesses（重取 PID——进程可能已重启）
→ selectProcess + attach（重取 processStartTime / mapRevision）
→ 读 mcp_analysis.json（恢复已验证结论，避免重做）
→ 继续
```
本项目把这套"每次新进程都必须执行"的清单（14 步）写成了可复跑操作清单——
**恢复流程 = 初始化流程，同一份清单两用**，这是省下的最大重复劳动。

## §11 控制通道与数据通道分离：大文件绝不走协议

> 🔴 **协议是"控制平面"，不是"数据平面"。**
> 把所有东西都塞进同一条通道，是"响应打爆上下文"与"协议性能崩塌"的共同根因。

### 11.1 为什么大文件不能走协议

| 问题 | 机制 |
|---|---|
| **体积膨胀** | hex/JSON 编码让二进制膨胀 2 倍以上（本项目 NDJSON：hex 编码膨胀 2×） |
| **解析开销** | 几十 MB 的 JSON 解析本身就慢且吃内存，两端都吃 |
| **撑爆响应上限** | 违反 §3.2 单响应 ≤4K token 硬约束，直接打爆 AI 上下文 |
| **无断点续传** | 协议通道传一半断了，没有天然的恢复机制 |

### 11.2 双通道架构（本项目铁律）

| 数据类型 | 通道 | 机制 |
|---|---|---|
| 命令 / 扫描结果 / 小内存读 / 日志 / 状态 | **控制通道**（NDJSON over socket） | 分页 + `brief` + 响应上限 |
| **产物文件**（几十 MB 的 SDK/转储/日志包） | **数据通道**（独立传输） | 不走 socket |

数据通道的标准流程：
1. 后端把产物**落盘到约定目录**（如 `/sdcard/UnrealMemoryTools/<target>/` 或服务器磁盘）；
2. 控制通道只传**元数据**：`listOutputFiles` 返回文件名/大小/mtime/hash，**不返回内容**；
3. 需要完整文件时：
   - 优先**服务端过滤**（`searchClasses` / `describeClass`：只回"那一个类"的定义，几 KB）；
   - 确实要整文件 → 独立通道直拉（本项目 `adb pull`；服务器场景就是 HTTP 下载 / `scp`），
     **拉取后本地校验 hash**；
4. 协议对"超大响应"提供**分块帧格式**作为兜底（§11.3），但这是例外不是常态。

### 11.3 分块帧格式（确实超一帧时的兜底）

```
{"id":1,"ok":true,"seq":0,"total":3,"data":{"chunk":"..."}}
{"id":1,"ok":true,"seq":1,"total":3,"data":{"chunk":"..."}}
{"id":1,"ok":true,"seq":2,"total":3,"data":{"chunk":"..."}}
```
- 同一 `id`，`seq` 从 0 递增（幂等：可按 seq 重传单帧）；
- `total` 为总帧数，最后一帧 `seq == total-1`；
- 客户端按 `id` 重组后再交给工具层；
- **只在"必须走协议的中等大文本"（如 `readOutputFile` 的大块文本）使用**，
  几十 MB 一律走独立数据通道。

### 11.4 泛化

- 任何 MCP 后端只要会产出"比一次响应大几个数量级"的产物（报告、图片、数据库导出、
  二进制转储），都应有"**落盘 + 元数据 + 服务端过滤 + 独立拉取**"四件套；
- MCP `resources` **只适合小资源**（进程列表、几十 KB 的探测结果、日志摘要）；
  **大文件绝不做 resource**——客户端可能整个读进上下文（§3.4）；
- 元数据里的 **hash 是验收依据**：拉取后校验，不匹配就是"任务失败"（§17）。

## §12 并发与线程模型：串行协议、命令分级、阻塞 I/O 隔离

> 🔴 三条规则，各对应一个真实故障：**协议不串行**会乱序，**命令不分级**会误判掉线，
> **阻塞 I/O 不隔离**会卡死整个服务。

### 12.1 设备协议：严格请求-响应串行

- 后端协议是"**发一收一**"，不是全双工；
- 客户端用 `RLock`（或等价锁）**串行化所有后端调用**；
- MCP 允许并行 tool calls，但客户端排队顺序执行——**正确，延迟叠加可忽略**
  （真正耗时在后端执行，不在协议层）；
- **不要为不存在的并发过度设计**：单对单场景下，加 `reqId`/连接池是过度设计；
  若将来真出现多客户端，协议加 `reqId` 做请求-响应匹配，那时再做（本项目 v1 明确不做）。

### 12.2 后端命令分级（快命令直执行 / 重活投 worker）

> 🔴 后端若是单 worker 线程，分钟级重活期间 `ping`/`getLogs`/状态查询**全部排队**
> → AI 误判掉线 → 触发重试风暴。分级是单 worker 模型的生存前提。

```
快命令（命令线程直接执行，不进 worker）：
  PING / GET_CAPABILITIES / GET_LOGS / GET_*_STATUS / LIST_PROCESSES /
  小内存读 / 符号解析 / 采样 / 取消 / 会话结束 …
重活（投递 worker 线程）：
  全内存扫描 / Probe / Dump / 高层编排 / 远程调用 …
```
- 分级表**写进协议文档**（§2.2 第 8 条），客户端的 `waitMs` 选择依赖它；
- 两类命令共享的数据要有互斥保护（本项目以 `DumpUiState` mutex 保护的数据为界，
  避免竞态）；
- **worker 内要埋协作式取消点**（§6.1 件套 5）。

### 12.3 客户端：阻塞 I/O 必须隔离到线程 🔴

> **FastMCP 是 asyncio 的，而设备/后端 I/O 是阻塞的。
> 绝不能在 async 函数里直接做同步 socket 调用——会卡死整个事件循环。**

```python
# ✅ 正确：阻塞 I/O 丢到线程池
result = await asyncio.to_thread(bridge.call, command)

# ❌ 错误：卡死事件循环 → progress / cancel / 其他工具全部停摆
result = bridge.call(command)
```
- **所有**走后端 socket 的调用都要这么包（一条都不能漏）；
- 心跳接收、重连逻辑放**独立后台线程/任务**，与命令调用解耦；
- 配套：单命令等待要有**软超时**（本项目 `SOCKET_TIMEOUT` 60s），
  到点中断等待并探活，不能无限阻塞。

### 12.4 后端线程模型的"最小侵入"原则 🟠

把命令服务挂进一个**已有主循环的 GUI/应用进程**时（本项目：ImGui 渲染循环）：
- **一条已有线程模型都不改**：复用既有的 worker 线程 + 状态 mutex 模式；
- 侵入点压到最小：`main()` 里起命令线程（几行），主循环每帧 `poll` 一次命令队列（几行）；
- 好处：命令服务崩溃/异常**不波及渲染主循环**；渲染卡顿也**不丢失命令**（队列缓冲）。
- 泛化：给"有主循环的宿主进程"加任何常驻服务，都优先"起独立线程 + 主循环每帧 poll"，
  不要改造宿主主循环。

## §13 技术栈选型：官方 SDK vs 手写、asyncio 的坑

> 🟠 选型错误的代价 = 把 SDK 白送的能力**重做一遍还做错**。
> 本节给出本项目用"排除法"做技术选型的完整推理，任何 MCP 项目可照此打分。

### 13.1 先纠正一个前提：源项目的手写实现不是范本

本项目参考的源项目 `mcp_server.py` **不是 FastMCP**，是纯标准库手写
（import 仅 `argparse/json/math/os/socket/struct/subprocess/sys/threading/...`，
无任何 MCP SDK，JSON-RPC 2.0 手工实现）。
它的限制（无 resources、无 logging、无 progress、无取消、单线程阻塞）**是手写实现的代价，
不是 MCP 本身的限制**——不要把它当范本照抄，也不要因此低估 MCP SDK 的价值。

### 13.2 选型打分法（本项目实例）

**按"本项目权重"打分，而不是按"通用最佳实践"打分：**

| 方案 | 关键依赖(反汇编) | 需要的功能 | 依赖量 | 传输抽象 | 平台 | 结论 |
|---|---|---|---|---|---|---|
| Python + 官方 SDK (FastMCP) | ✅ 原生绑定 | ✅ 全有 | 中 | ✅ | ✅ | **选它** |
| TypeScript + 官方 SDK | ❌ WASM/原生插件，生态弱 | ✅ 全有 | 大 | ✅ | ✅ | 反汇编卡死 |
| Python 纯手写（照抄源项目） | ✅ | ❌ 全要自己做 | 极小 | ❌ 自己写 | ✅ | 重蹈覆辙 |
| C++ / 其他 | 麻烦 | 麻烦 | — | — | — | 排除 |

**决定项排序（先定"卡脖子项"，再定"加分项"）：**
1. **第一决定项：核心依赖的生态**。本项目的 `disassemble` 是核心工具
   （解密 FName 要靠它读汇编），Python 有成熟 capstone 原生绑定，Node 生态弱
   （capstonejs 长期失修）——**这一条直接排除 TypeScript**。
2. **第二决定项：SDK 白送的能力**。resources、logging、progress、cancellation——
   正是审查里要补的东西；手写等于把 SDK 的活重做一遍，还容易做错。
3. 其余（依赖量、平台）是次要项。

> 泛化：MCP 选型先问两个问题——
> ① 你的"卡脖子依赖"（反汇编/数据库/系统调用/硬件）在哪个语言生态最强？
> ② 你需要的 MCP 高级能力（resources/logging/progress/cancel/dynamic tools）
>    在哪个 SDK 里是白送的？
> 两者交集就是你的答案。

### 13.3 选 SDK 的三个"版本纪律"

1. **用官方 SDK，不用同名社区包**（本项目：`mcp.server.fastmcp`，
   不用第三方 `fastmcp` 包——社区版与官方协议节奏不同步）；
2. **锁版本**：MCP 协议一年迭代多个版本，SDK churn 快，`requirements.txt` / 锁文件必须 pin；
3. **协议版本协商**（§2.3）：SDK 升级后协议可能变，握手版本号是升级时的安全网。

### 13.4 asyncio 的两个坑（选 Python 必须知道）

1. **阻塞 I/O 卡死事件循环**（§12.3）——所有同步后端 I/O 走 `asyncio.to_thread`；
2. **Pydantic schema 与文档漂移**：几十个工具手写 `inputSchema`/`outputSchema` 极易与实现漂移。
   对策：用**类型注解 + Pydantic 自动生成** schema，再写单测**反过来校验**
   "文档里的 JSON Schema 与生成的一致"——schema 是"文档-实现"的契约锚点。

### 13.5 后端的依赖纪律 🟡

- 后端（设备端/嵌入场景）**零新增依赖**或极少依赖；
  本项目后端 JSON 统一用 `nlohmann/json`（header-only，仓库已有，禁止再造轮子手写解析——
  手写解析是 v1.0 安全/兼容问题的根因之一）；
- 客户端（PC/服务器）依赖"少而锁定"，全部集中在客户端，不扩散到后端。

### 13.6 "有理由的偏离"要记录 🟡

选型/设计中对"最佳实践"的**任何偏离都要书面记录理由**（本项目示例）：
- "避免描述性错误"不采纳——理由是本地单用户调试工具，详细错误是核心功能（§7.3）；
- 不用 Docker 打包——需要 adb + 真机 + root，容器化无收益；
- 协议严格串行不做 reqId——单对单，并发恒为 1（§12.1）。
> 记录不是形式主义：6 个月后（或换人接手时），"为什么这里不合规"的答案只在文档里。

## §14 测试体系：契约测试、故障注入、Mock 后端

> 🔴 **测试左移**：契约测试与故障注入从 Phase 1 就建，不是上线前补。
> MCP 测试的核心难点：**后端往往是"真机/外部系统"，不能每次测试都连真机。**

### 14.1 四层测试金字塔

| 层 | 内容 | 依赖真机 | 何时跑 |
|---|---|---|---|
| **单元** | 协议帧编解码、hex/struct 编解码、参数校验、schema 生成 | ❌ | 每次提交 |
| **契约** | 每个工具返回严格符合 `outputSchema`（**自动化校验**）；两端共用的"黄金样例" | ❌（mock 后端） | 每次提交 |
| **故障注入** | 见 §14.3 | ❌（mock 模拟故障） | 每次提交 |
| **集成** | 真实后端跑完整用例（有 ground truth） | ✅ | 里程碑 / 发版前 |

### 14.2 契约测试：两端共用"黄金样例" 🔴

- 为**每个命令**准备一对黄金样例：`<cmd>.request.json` + `<cmd>.response.json`
  （本项目 `tests/contract/`：MVP 三命令各一对，后续逐批补）；
- **两端测试都引用同一份样例**：PC 侧 Python 解析、设备端 C++ 解析，各自断言——
  这就把"两端理解不一致"从"上线后发现"提前到"CI 红"；
- schema 契约：工具 `outputSchema`（Pydantic 生成）与实际返回 `structuredContent`
  **逐字段一致性**用测试强制（§13.4：反过来校验文档 JSON Schema 与生成的一致）。

### 14.3 故障注入清单（MCP 特有，必测）

> 这些故障**在正常开发路径里永远不会自然发生**，不专门注入就永远测不到：

| 注入场景 | 断言 |
|---|---|
| **漏调会话结束**（有状态工具泄漏） | 看门狗/TTL **必须**自动结束（§5.2 四重兜底） |
| **写不可写地址** | **必须拒绝**执行并返回中性说明，不尝试写（§9.2） |
| **目标进程消失**（ESRCH / 进程退出） | 清理状态并**正常返回**错误码，不抛异常、不泄漏（§5.2） |
| **断线重连**（kill 后端 → 重启） | 指数退避重连成功 + 重新 HELLO + 旧 sessionId 失效 + in-flight 调用 `isError:true`（§10） |
| **心跳停止**（mock 后端不再发心跳） | 超 10s 判假死 → 断开重连，旧 job 作废（§6.1/§10.3） |
| **长任务超时**（mock 后端卡死） | 硬超时触发 → 返回 `E_TIMEOUT` + progress，不无限阻塞（§6.1） |
| **协议版本不匹配**（mock 后端回旧 protocol） | 立即断开 + 明确报错，不让后续命令"一路失败"（§2.3） |
| **超大响应**（mock 后端回 64KB hex） | 被分页/截断到 ≤4K token，返回 `nextCursor`（§3.2） |
| **参数非法**（未知工具/坏 schema） | 返回**协议层** JSON-RPC error，而非 `isError:true`（§7.1 分层） |

### 14.4 Mock 后端：不依赖真机即可开发 🔴

- 契约/故障注入测试跑在一个 **mock 后端**（本项目 `tests/conftest.py`）上——
  它实现同一份 wire protocol（HELLO/心跳/命令表/错误码），但逻辑是假的；
- **协议文档是 mock 与真机的共同规格**：mock 按 `docs/mcp-protocol.md` 实现，
  真机也按它实现——所以"mock 下全绿 + 真机一次跑通"是 Phase 1 的 DoD；
- 价值：**80% 的开发（PC 侧 bridge/工具层/测试）不需要真机**，
  真机只在里程碑做集成验证——大幅降低"编译→推包→重启游戏"的循环成本。

### 14.5 集成测试的"ground truth"原则 🟠

- 集成测试必须跑在**已知答案的目标**上（本项目：`元梦之星` 作为定位用例的 ground truth，
  `式神契约`/`卡拉彼丘` 作为完整 Dump 的回归目标）；
- 断言用**不变量**（§8.5）而非具体数值：
  "FName 前 16 项含引擎内建名" ✅，"GNames 地址 == 0x7970d275c0" ❌（地址随 ASLR/构建变）；
- 回归基线**存不变量断言 + 产物 hash**，不存"绝对地址"。

## §15 工程流程：契约冻结 → Walking Skeleton → 垂直切片 → 铺开 → 质量门禁

> 本章是本项目路线图的**通用化**。核心理念：**把风险前移**——
> 用最便宜的交付物（文档、一个命令、一条切片）尽早暴露最贵的风险（架构错、协议错、阻塞 I/O）。

### 15.1 五条原则

1. **契约先行（Contract First）**：两端/多端是独立二进制，先用协议文档解耦，
   并行开发互不等待（§2）。
2. **Walking Skeleton（先跑通最薄端到端链路）**：Phase 1 只做"3 个命令打通真机"，
   把架构里 13 项风险（bind/断线/阻塞 I/O/心跳…）在投入大批量代码前暴露。
3. **垂直切片优先于水平铺开**：先完成**一条完整业务用例**（端到端，从输入到产物），
   再横向补齐其余工具。避免"所有层都写一半、没有一个能跑"。
4. **测试左移**：契约测试、故障注入从 Phase 1 就建（§14）。
5. **每步可独立验证、可回滚**：每个 Phase 有明确 **DoD（完成定义）**，不满足不进下一阶段。

### 15.2 五阶段模板（带 DoD）

| Phase | 目标 | DoD（完成定义） |
|---|---|---|
| **0 契约冻结** | 协议文档 + 全工具 schema + 契约黄金样例 | 协议评审通过；schema 与工具规格逐字段一致；黄金样例可被两端测试引用 |
| **1 Walking Skeleton** | 最薄链路：N 个 MVP 命令（本项目 3 个）打通真机 | 客户端 ping 返回**真实**后端 build+protocol；断线重连可演示；单测覆盖协议收发 |
| **2 MVP 垂直切片** | 一条完整业务用例端到端（本项目：定位引擎全局） | 真机 ground truth 走通；证据内嵌；单响应 ≤4K token |
| **3 全量铺开** | 按"依赖+性价比"分批补齐所有工具 | 每批：全工具含 schema+annotations+触发词+耗时档位；契约测试通过 |
| **4 质量加固** | 质量门禁（§18）全过 | 契约/故障注入/token 预算/安全 四类门禁全绿 |
| **5 集成验证与发布** | 真机全流程回归 + 文档同步 | 回归通过；文档与代码同步；PR 写明每工具增加的常驻 token |

> 分批展开（Phase 3）的排序依据是"**依赖 + 性价比**"：
> 先做"后端能力已有、只需封装"的原语层（最划算），再做"需要外迁/参数化"的，
> 最后做"全新能力 + 高危"的（如远程调用）。本项目批次：
> 3.1 原语层（直接包装已有能力）→ 3.2 外迁（移出匿名 namespace + 参数化）
> → 3.3 ptrace 接线 → 3.4 新建（语义查询 + 高层编排 + 复合操作）。

### 15.3 "先验证最有价值的反馈点，再投大批量代码" 🟠

> 本项目推进策略原话：**"ping 一打通就能拿到真实 deviceBuild + protocolVersion，
> 这是最有价值的反馈点——证明'AI 能驱动真机'走得通，再投入剩下 3000 行才不冒险。"**

泛化成决策规则：
- 在投入 N 倍于骨架的代码量之前，先确认**最小链路在真实环境成立**；
- "真实环境成立"的证据 = 真实后端的真实元数据返回（不是 mock 的）；
- 如果最小链路在真实环境都跑不通（权限/网络/协议），后面 10000 行全是空中楼阁。

### 15.4 单人开发的"串行推进" 🟡

> 本项目明确：**单人开发并行无收益**——推进策略是严格串行：
> 协议定稿 → 后端服务端 → 客户端对接+真机联调 → 再铺开工具。
> 原因：单人场景下，并行写两端 = 两端都在"猜对方的接口"，协议没冻结前并行是负收益。
> （多人/多端团队例外：契约冻结后两端**可以**并行——这正是契约先行的价值。）

### 15.5 里程碑命名（M1…M6）

用**可验证的里程碑名**而非日期（本项目：M1 契约冻结 → M2 端到端 ping 打通 →
M3 定位用例闭环 → M4 全工具齐 → M5 质量门禁过 → M6 真机发布）。
每个里程碑 = 一个可独立验收的状态，**不设工时**（避免"按计划赶工"导致门禁失守）。

## §16 文档 > 源码：为什么文档才是资产

> 🔴 **本项目 README 的核心主张："最值钱的部分不是代码，而是沉淀下来的工程经验。"**
> 这一节把"为什么"讲透，并给出"文档体系应该长什么样"的可操作结构。

### 16.1 为什么文档比源码更值钱（四条论据）

1. **源码是静态的**：改一行就过期；文档里的经验（"为什么 NumElements 是 0x10 不是 0x14"、
   "为什么禁用 isPtrWritable"）**跨版本有效**。
2. **源码不解释"为什么"**：协议设计、token 约束、安全取舍——这些"决策的理由"只在文档里。
   6 个月后没人记得"当时为什么这么定"，重做决策 = 重踩坑。
3. **源码有歧义**：API 行为、边界条件、空值语义（"偏移 0 表示不支持"还是"偏移就是 0"？）
   ——文档用自然语言消除歧义。**本项目 14 份 API 精读文档，核心工作就是
   "把源码里隐含的语义显式化"**（每份都有"全局约定：读代码前必知"一节）。
4. **源码不记录历史**：为什么走了 A 方案不是 B 方案、为什么"有理由的偏离"
   （§13.6）、哪次事故催生了哪条规则——这些只在修订记录里
   （本项目架构文档的 v1.1/v1.2 修订表，每条都标"严重度 + 修复位置"）。

### 16.2 "文档驱动开发"的操作定义

> **"任何一端改动，必须先改文档再改代码。文档是唯一的对齐事实。"**

- 协议改动：先改 `mcp-protocol.md` → 两端各自跟进 → 契约测试验证两端一致；
- 工具改动：先改工具规格（input/output/约束）→ 再实现 → 契约测试验证 schema 一致；
- 事故处理：先写"修正手册"（现象 + 根因 + 修复 + 为什么）→ 再改代码 →
  把新规则**回写到架构/协议文档**（否则同类事故必然复发）。

### 16.3 一个完整 MCP 项目的文档体系结构（可直接抄）

| 层 | 文档 | 回答的问题 | 本项目对应 |
|---|---|---|---|
| **入门** | 总 README | 这是什么、怎么跑、文档阅读顺序 | `README.md` |
| **目标** | 功能说明 | 做什么、为什么做 | `…功能说明.md` |
| **架构** | 开发必读架构 | 怎么写、规范、约束、修订记录 | `…开发必读架构.md` |
| **契约** | 协议文档 | 两端怎么对齐（唯一事实） | `mcp-protocol.md` |
| **规格** | 工具功能规格 | 每个工具的输入输出约束 | `…MCP工具功能规格.md` |
| **实施** | 开发步骤 + 路线图 | 怎么分阶段落地、DoD | `mcp_server开发步骤.md` / `MCP开发路线图.md` |
| **精读** | 后端 API 精读（按模块） | 后端每个模块的**显式语义**（空值/边界/线程安全） | `docs/api/00-14` |
| **改动** | 改动代码文档 | 新版 vs 旧版改了什么 | `UMT_改动代码文档.md` |
| **事故** | 修正手册 / 修复总结 | 事故现象+根因+修复+规则回写 | `…修正文档手册.md` / `UE偏移表Bug修复总结.md` |
| **经验** | 实战经验文档 | 真实目标上的完整流程 + 排查决策树 + 复跑口诀 | `式神契约…文档.md` / `卡拉彼丘…建议.md` |
| **判定** | 判定规则 / pattern 库 | 领域的"不变量清单"与特征码库 | `SDK分析判定规则.md` / `ue_pattern_library.md` |

### 16.4 文档的三个"反直觉"实践

1. **修订记录按"严重度"排序**（本项目 v1.2 修订表：前三条标"事故级"）——
   让读者 10 秒内知道"最该注意的是什么"；
2. **"读代码前必知"前置**：每份 API 精读第一屏就是"全局约定"（单例/线程安全/空值语义），
   而不是函数签名——**语义错比签名错致命 10 倍**；
3. **失败样本与成功样本同等归档**（§8 经验）：卡拉彼丘（失败）与式神契约（成功）
   并列存放——**失败样本是"快速识别同类陷阱"的最快路径**，删掉它等于下次重踩。

### 16.5 文档与代码的"一致性守护"

- 文档里的**契约样例**（黄金 JSON）被两端测试引用 → 文档改动 = 测试改动，漂移立即暴露；
- 文档里的**常量**（端口/超时/上限）在代码里定义为**单一常量源**（本项目 `config.py`），
  文档引用常量名而非重复数值；
- 每次 PR：文档与代码**同 PR 提交**，review 时二者对照——"只改代码不改文档"的 PR 打回。

## §17 成功判定：任务完成 ≠ 语义正确

> 🔴 **本项目最重要的实战教训（来自两次真实 Dump 对照）：**
> **"任务完成"只代表导出流程结束，不代表结果语义正确。**
> `success=true` 必须配合**一组语义断言**才算真成功——这是 MCP 工具的"验收哲学"。

### 17.1 真实案例：两次 Dump，一成一败

| | 式神契约（成功） | 卡拉彼丘（"成功"但失败） |
|---|---|---|
| Probe | `success=true` | `success=true`（**表面**） |
| Dump | `dumpPercent=100, success=true` | `success=true`（**表面**） |
| 产物 | 完整 SDK 文件集合，Objects.txt 3.7MB 可读 | **无** SDK_Classes/Structs/Enums 等文件，Objects.txt 只有几十字节 |
| 名称 | `Package CoreUObject` / `Class CoreUObject.Object` 连续可读 | `adObject`、`ject`、`ct` 等**错位半词** + 大量 `�` |
| 日志 | `RunFixup done (success=1)`，`NamePrivate/ClassPrivate validated` | `GetObjectPtr(1).GetIndex() != 1`、`ERROR_EMPTY_PACKAGES` |

**关键洞察**：卡拉彼丘的 `success=true` 是**流程成功**（"我把文件写出来了"），
不是**语义成功**（"我写出来的是对的"）。根因：低置信度候选被当成最终地址
（候选落在静态 ASCII 表上，被误认为 FNamePool）+ `mapRevision` 在长任务中变化。

### 17.2 通用原则：把"成功"拆成"流程成功 + 语义成功"两级

任何会产生"产物/结论"的 MCP 工具族，都必须定义**两级成功**：
1. **流程成功**：执行没报错、状态机走到终态、文件写出来了；
2. **语义成功**：产物内容满足一组**领域不变量断言**。
**只有两级都满足，才允许对 AI 报"成功"。** 否则报"流程完成但语义未验证"，
并把未通过的断言逐条列出（让 AI 知道该修哪里）。

### 17.3 "语义成功断言清单"的构造方法（不变量法）

> 断言必须是**"所有合法目标上都必然成立"**的特征，不是"本次观察到的值"。

以本项目 UE Dump 为例（其他领域照此构造自己的清单）：
| # | 断言 | 类型 |
|---|---|---|
| 1 | FName ID 0 解析为 `None` | 不变量（引擎内建） |
| 2 | FName 前 16 项含 `ByteProperty/IntProperty/BoolProperty/…` | 不变量（引擎内建） |
| 3 | 对象数组前 N 个对象全名含 `/Script/CoreUObject` | 不变量（引擎内建） |
| 4 | 出现 `Package`、`Class` 等核心锚点名称 | 不变量 |
| 5 | `NamePrivate`/`ClassPrivate`/`OuterPrivate` 校验通过（`validated`） | 内部一致性 |
| 6 | 产物文件集合**完整**（每个预期文件都在） | 完备性 |
| 7 | 关键产物**大小达阈值**（Objects.txt 不能只有几十字节） | 量级 |
| 8 | 产物**无大面积替换字符/半词** | 形态 |
| 9 | `dumpPercent=100` 且 `success=true` | 流程 |
| 10 | 产物 **hash 可复核**（manifest 内 hash 与文件一致） | 完整性 |

**"只满足'文件存在'不算成功"**——文件存在只是断言 6 的一部分，10 条全过才算。

### 17.4 失败结果也要"归档为对照样本" 🟠

- 失败产物（乱码的 Objects.txt、不完整的 SDK）**保留**，标注"失败样本 + 失败原因"；
- 价值：失败样本是**"快速识别同类陷阱"的最快路径**——
  下次再出现"半词名称"，直接对照样本的根因（静态 ASCII 表冒充名字池），
  不用重新排查。**删掉失败样本 = 下次重踩同一个坑。**
- 归档时附"失败决策树"（本项目乱码排查决策树：
  "Objects.txt 是否可读？否→名称是半词？检查候选是否落入静态 ASCII…是→抽样 CoreUObject…")，
  让"失败"变成"可诊断的失败"。

### 17.5 "硬闸门"：语义未过不生成"看似成功"的产物 🔴

- 关键导出工具（`startDump`）应在**导出前执行硬校验**（§17.3 断言的前置子集）；
- 失败时**不生成**"看似成功"的产物（否则会污染下游：AI/人拿到"成功文件"就不再验证）；
- 输出 **manifest**（`dump_manifest.json`）：记录每个文件的路径、大小、hash、验证状态，
  manifest 本身成为"语义成功"的可机读凭证。

## §18 质量门禁（Quality Gates）

> 门禁是**可机检的硬约束**，不是"建议"。每个门禁对应前文一条规则，
> Phase 4 必须全绿才能进 Phase 5。门禁的价值：把"§3–§12 的所有设计纪律"
> 变成 CI 里能红/绿的检查项——**纪律不落到门禁上，就一定会在某次赶工时失守。**

### 18.1 四类门禁

| 门禁类 | 检查项（机检） | 对应章节 |
|---|---|---|
| **契约** | 每工具返回严格符合 `outputSchema`（自动化校验）；黄金样例两端可解析 | §2, §4.2, §14.2 |
| **故障注入** | §14.3 全清单：看门狗触发 / 写不可写必拒 / ESRCH 正常返回 / 断线重连 / 心跳停 / 超时 / 版本不匹配 / 超大响应分页 / 参数非法分层 | §5, §6, §7, §10, §14.3 |
| **token 预算** | 单响应 ≤4K token（超大响应被分页）；常驻工具 ≤25（动态组正确挂载/摘除）；`brief` 生效 | §3 |
| **安全** | bind 仅回环（非回环需显式配置）；`confirm_dangerous` 生效（false 时不执行）；写前校验生效；`getCapabilities` 能报告泄漏会话 | §5, §9 |

### 18.2 门禁的"不可绕过"性

- 门禁跑在 **CI**（每次提交 / 每个 PR），不跑在"发版前手动点一遍"；
- 门禁**红 = 合入阻塞**，没有"先合入后补"的口子（补了 = 门禁失效）；
- 每个门禁项有**对应测试文件**（本项目 `tests/test_contract.py` / `test_fault_injection.py`），
  门禁不是"脚本"而是"测试套件"——可维护、可扩展。

### 18.3 门禁与"有理由的偏离"的关系

- 门禁检查的是**纪律**（§3–§12），不是"最佳实践字面"；
- 对最佳实践的**有理由偏离**（§13.6）要**记录在文档**，但**不绕过门禁**——
  例如"详细错误是功能"偏离的是"错误描述规范"，但"错误分层"门禁照样跑
  （详细 ≠ 不分层）。偏离记录与门禁是两套东西：前者解释"为什么这样设计"，
  后者强制"底线不可破"。

## §20 附录：可直接抄的骨架与速查表

> 本附录把所有"散落在各章的骨架"集中成**可直接复制到新项目**的模板。
> 占位符用 `<...>` 标注。

### A. 工具定义骨架（Python / FastMCP，含"四件套"全字段）

```python
@mcp.tool(
    name="scanXxx",                       # camelCase 动词开头（§4.1）
    title="扫描 <X> 候选",                 # 中文 title（§4.2）
    annotations={                          # annotations 必给（§4.2）
        "readOnlyHint": True,
        "destructiveHint": False,
        "idempotentHint": True,
        "openWorldHint": False,
    },
)
async def scan_xxx(
    anchor_names: list[str] = Field(
        default=["A", "B", "C"],
        description="锚点，建议至少 3 个（单锚点误判率高）"),
    max_candidates: int = Field(default=50, ge=1, le=2000),
    brief: bool = Field(default=False, description="true=只回统计+前N摘要"),
    cursor: str = Field(default="", description="分页游标，续读上一页"),
) -> dict:
    """<use_case>在目标中扫描 <X> 的候选地址。</use_case>
    <important_notes>
    1. 前置：先调 detectVersion 确认版本，缩小范围。
    2. 耗时档位：慢 <5min（大目标分钟级）。
    3. 只返回候选摘要，必须用 sampleXxx 取样本后判定。
    4. 成功→sampleXxx；失败→放宽 anchorNames 重试或看 getLogs。
    </important_notes>
    别名：找函数 / 定位特征码 / 搜 pattern。"""
    # 🔴 阻塞 I/O 必须丢线程，否则卡死事件循环（§12.3）
    return await asyncio.to_thread(bridge.call, "SCAN_XXX", {
        "anchorNamesHex": to_hex(anchor_names),   # 字符串参数 hex 传输
        "maxCandidates": max_candidates,
        "brief": brief, "cursor": cursor,
    })
```
> 要点回链：name camelCase（§4.1）；四件套（§4.2）；描述含 use_case/notes/耗时档位/别名/下一步（§4.5）；
> 阻塞 I/O 走 to_thread（§12.3）；hex 传输（§2 编码约定）。

### B. 协议骨架（wire protocol 最小集）

```
传输：TCP，后端 bind("127.0.0.1", <port>)，仅经隧道暴露（§9.1）
帧  ：NDJSON（每行一个 JSON，\n 结尾）

握手（后端 → 前端，连接建立后立即）：
  {"type":"hello","protocol":1,"build":"<ver>","capabilities":["<CMD>","..."]}
前端校验 protocol，不匹配 → 明确报错并 close()（§2.3）

请求（前端 → 后端）：
  {"id":<n>,"cmd":"<CMD>","args":{...}}        # id 单调递增，串行
成功：
  {"id":<n>,"ok":true,"data":{...}}
失败：
  {"id":<n>,"ok":false,"error":{"code":"<E_*>","msg":"...","detail":{...}}}
长任务未完成：
  {"id":<n>,"ok":true,"data":{"jobId":"j-1","status":"running",
    "progress":0.42,"etaSeconds":18,"suggestedWaitMs":15000}}
心跳（后端 → 前端，每 2s，无论是否有请求）：
  {"type":"heartbeat","ts":<sec>,"busy":true,"activeJobId":"j-1"}
分块（超一帧兜底）：
  {"id":<n>,"ok":true,"seq":0,"total":3,"data":{"chunk":"..."}}  (seq 0..total-1)
```
常量：`HEARTBEAT_INTERVAL=2s` / `HEARTBEAT_TIMEOUT=10s` / `CMD_TIMEOUT=120s` /
`RECONNECT 1s→30s 指数退避` / `waitMs 默认5000 上限60000`（§6/§8 协议常量）。

### C. 错误码骨架（协议层 vs 执行层，分层必守）

| 错误码 | 层 | AI 应做什么 |
|---|---|---|
| `E_PROTOCOL_MISMATCH` | 协议 | 停止，报告需升级 |
| `E_BAD_JSON` / `E_BAD_ARGS` / `E_UNKNOWN_CMD` | 协议 | 改参数/工具名 |
| `E_NOT_ATTACHED` | 执行 | 先做前置 attach/选择 |
| `E_READ_FAILED` / `E_WRITE_FAILED` | 执行 | 查地址/换候选；写失败查映射可写性 |
| `E_NOT_READY` | 执行 | 先完成前置步骤（probe/选择） |
| `E_NOT_FOUND` | 执行 | 换搜索方式（特征码/放宽） |
| `E_TIMEOUT` | 执行 | 当"后端可能异常"，探活 |
| `E_CANCELLED` | 执行 | 重新发起 |
| `E_MAP_STALE` / `E_SESSION_STALE` | 执行 | 重新取快照/重建候选 |
| `E_INTERNAL` | 执行 | 看 getLogs |

> 分层规则：协议层 → JSON-RPC `error`；执行层 → `isError:true` tool result（§7.1）。

### D. 心跳 + 重连状态机（前端侧伪代码）

```
loop:
  收帧：
    heartbeat → 刷新 last_heartbeat；busy 则不判活失败
    response  → 配对 id 返回给 in-flight 调用
    其他      → 分派
  若 now - last_heartbeat > HEARTBEAT_TIMEOUT(10s):
      判定假死 → close() → 进入重连
重连：
  delay = 1s；循环 connect()：
    成功 → 重新 HELLO + 校验 protocol + 重新拉 capabilities
          → 所有 sessionId 标记失效（§10.2）
          → in-flight 调用返回 isError:true "连接已断开，已自动重连，请重试"
          → 恢复
    失败 → sleep(delay); delay = min(delay*2, 30s)
```

### E. 长任务工具骨架（waitMs 短等 + 超时转 job + 可取消）

```python
async def start_task(..., wait_ms: int = Field(default=5000, ge=0, le=60000)) -> dict:
    """<use_case>启动 <X> 流程。</use_case>
    <important_notes>耗时档位：慢 <5min。waitMs 内完成直接返回结果，
    超时返回 jobId 供轮询；可用 cancelJob 取消。</important_notes>"""
    return await asyncio.to_thread(bridge.call, "START_X", {"waitMs": wait_ms, ...})
# 返回二选一：
#   {"status":"done","result":{...}}                      # waitMs 内完成（1 次往返）
#   {"jobId":"j-1","status":"running","progress":0.0,     # 超时转轮询
#    "etaSeconds":60,"suggestedWaitMs":15000}
```

### F. 有状态工具"四重兜底"骨架

```python
class Session:
    def __init__(self, max_hold_ms=3000, idle_ms=...):
        self.max_hold = max_hold_ms      # ① 最长持有
        self.idle_ms = idle_ms           # ② 空闲看门狗
    def use(self, op):
        try:
            self._touch()                # 刷新 idle 计时
            return op()
        finally:
            if self._expired(): self.close()   # ①/② 触发即强制结束
    def on_exception(self, e):           # ③ 异常兜底：先结束再报错
        self.close()
        raise e
    def on_disconnect(self):             # ④ 断连兜底
        self.close()
# 暴露状态：getCapabilities 返回 activeSession: bool（§5.2 第3条）
# 目标消失（ESRCH）：close() 后正常返回错误码，不抛异常（§5.2）
```

### G. 常见坑速查表（现象 → 根因 → 章节）

| 现象 | 根因 | 章节 |
|---|---|---|
| AI 疯狂重试同一个慢工具 | 无耗时档位/无 suggestedWaitMs，AI 当"卡死" | §6.1/6.4 |
| 工具调用"卡死"无返回 | 无硬超时/无心跳，AI 分不清"在算"和"死了" | §6.1/6.4 |
| 上下文几轮就"失忆/乱猜" | 单响应超 4K token，或常驻工具过多 | §3 |
| AI 跳过验证直接下结论 | 证据未内嵌，"扫描-采样-判定"被压平 | §8.2 |
| AI 拿到"成功"文件其实是错的 | 只判流程成功，未判语义成功 | §17 |
| 游戏/目标被永久冻结 | 有状态工具漏调 end，无兜底 | §5 |
| 局域网设备能读写目标内存 | bind 0.0.0.0 + 无认证 + 内存写接口 | §9.1 |
| 重连后操作全错 | 重连未使旧 sessionId 失效 | §10.2 |
| 进度/取消全停摆 | 阻塞 I/O 没走 to_thread，卡死事件循环 | §12.3 |
| ping/日志在扫描期间无响应 | 后端单 worker，命令未分级 | §12.2 |
| 两端行为不一致且无人报错 | 协议未冻结/无版本协商/无契约测试 | §2/§14.2 |
| 改一处行为，文档与代码漂移 | 未"先文档后代码"+ 无 schema 一致性测试 | §16 |
| 大文件塞进响应直接爆炸 | 大文件走了控制通道 | §11 |
| "not found" 后 AI 放弃/乱猜 | 禁止负向表述被违反 | §4.3 |
| AI 分不清"调错"还是"后端失败" | 错误未分层 | §7.1 |
| 缓存命中 AI 以为是重扫 | 缓存不可见 | §4.7 |

### H. "先读文档再动手"——本文档的阅读路径建议
