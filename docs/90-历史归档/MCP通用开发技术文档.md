# 通用 MCP 服务器开发技术文档

> 适用范围：任何基于 Model Context Protocol 的服务端开发（Python/TypeScript，stdio/SSE 传输）。
> 经验来源：War3 地图生产 MCP 工作台（`war3mcptool`，477 个工具目录项、4 类地图管线、KKWE 加密解密集成）的完整踩坑档案与逆向工程实战。
> 配套阅读：`.trae/rules/War3MCP工具开发规则.md`（项目硬性纪律）、`.trae/rules/mcp构建工具工程师.md`（角色规范）。
>
> **一句话总纲：工具好不好用，不是你说了算，是智能体在真实任务里的表现说了算。**

---

## 0. 核心原则（全文档的 7 条锚）

| # | 原则 | 违反时的典型事故 |
|---|---|---|
| P1 | **从智能体视角设计工具**：智能体靠工具名和参数描述选工具、用工具 | 两个工具名太相似（`get_user` vs `fetch_user`）导致随机调错 |
| P2 | **假设必须被真实内容证伪，才准下结论** | 逆向时"解析跑通了、终点贴合文件尾"但常量恒为 0 —— 假成功，交付的全是错的 |
| P3 | **每个能力配一条验收链**：health → status → validate → compile/run | 改完就交，下游才发现引用缺失、包结构错误 |
| P4 | **能离线复现的，绝不依赖运行时**：静态特征、纯数学推断优先，逆 DLL/动态调试是最后手段 | opcode 置换本可纯数学解出，却先走了逆 DLL 弯路 |
| P5 | **门面薄、注册集中、实现下沉**：server 入口只做装配 | server.py 变成上帝文件，改一个工具要翻 3000 行 |
| P6 | **失败要优雅且可操作**：返回"发生了什么 + 下一步做什么"，不裸抛、不吞栈 | 错误信息是"操作失败"四个字，智能体陷入无限重试 |
| P7 | **写操作永远有闸门**：高风险工具必须显式确认/快照/回滚路径 | 智能体 hallucination 触发删除/编译，工程被改坏且不可恢复 |

## 1. 总体分层架构

一个可维护的 MCP 服务器，按职责切成 7 层。每层只依赖下一层，不允许跨层调用。

```text
┌─────────────────────────────────────────────────────────┐
│ L7  客户端接入层   mcp.json / IDE 连接器 / 环境变量        │  ← 第 9 节
├─────────────────────────────────────────────────────────┤
│ L6  门面层         server.py（FastMCP 实例 + 装配，不写逻辑）│  ← 第 2.1 节
├─────────────────────────────────────────────────────────┤
│ L5  工具注册层     mcp_tools/*.py（薄封装：TOOL_NAMES + 参数）│  ← 第 2.3 节
├─────────────────────────────────────────────────────────┤
│ L4  能力层         core/<子包>/（按领域：对象/地形/脚本/资源…）│  ← 第 2.4 节
├─────────────────────────────────────────────────────────┤
│ L3  验证与门禁层   validation/（质量门禁、引用检查、契约校验）│  ← 第 6 节
├─────────────────────────────────────────────────────────┤
│ L2  外部集成层     integrations/（外部 CLI/DLL/引擎适配）   │  ← 第 7 节
├─────────────────────────────────────────────────────────┤
│ L1  资源与配置层   res/ 快照、config.py、paths.py（路径安全）│  ← 第 5.2 节
└─────────────────────────────────────────────────────────┘
```

### 1.1 各层职责与反例

| 层 | 职责 | 反例（真实踩坑） |
|---|---|---|
| 门面层 | 创建 MCP 实例、注册聚合、共享 helper | 把业务逻辑写进 server.py，最后膨胀到无法维护 |
| 注册层 | 工具声明、参数 schema、薄函数转发 payload | 在注册层写 200 行业务逻辑，工具模块变成第二能力层 |
| 能力层 | 真正的业务实现，按领域分子包 | 所有功能堆在一个大文件里，"持续叠加屎山" |
| 门禁层 | 只读校验 + 错误码 + 修复建议 | 校验逻辑散落在各写工具内部，无法独立调用 |
| 集成层 | 封装外部程序（CLI、DLL、引擎），隔离其接口变化 | 外部 CLI 的解析散落在业务代码里，换版本全线崩 |
| 资源层 | 静态数据快照、路径解析、配置 | 运行时去源仓库拉数据，源一改全变 |

### 1.2 兼容 shim 的纪律

重构把大文件拆成子包时，旧 import 路径用**薄 shim**（`from .objects import xxx`）保持兼容，但：

1. shim 只允许 `import`/`__all__` 转发，**一行逻辑都不许有**；
2. 新代码一律从子包 import，shim 路径**只减不增**；
3. 在 README 里标注 "root 目录 `*.py` 是兼容面，不是推荐 import 路径"，防止后人把 shim 当实现位置继续堆代码。

## 2. 服务器骨架设计

### 2.1 门面层：server.py 只做三件事

```python
# server.py —— 目标长度：几百行以内
class War3MCPServer:
    def __init__(self):
        self.mcp = FastMCP("war3-map-builder")
        # 1) 装配：按模块注册表逐个挂载
        for module in REGISTERED_TOOL_MODULES:
            register_module(self, module)
        # 2) 懒加载表：payload 模块不启动时导入（首包启动时间敏感）
        self._lazy = _LAZY_IMPORTS
        # 3) 共享 helper：路径校验、日志、错误包装

    def get_payload(self, name):
        # 首次调用才 import，失败统一转 ToolError
        ...
```

**要点：**
- **懒加载（lazy import）**：工具模块多（本项目 20 个注册模块、477 目录项）时，启动时全量 import 会让首包慢到客户端超时。注册表只记名字，payload 模块在**首次调用**时才 import。
- 门面层可以持有**共享 helper**（路径校验、ToolError 包装、日志器），但**不能持有业务状态机**。

### 2.2 工具模块的标准形态

每个 `mcp_tools/<domain>.py` 固定三件套：

```python
# mcp_tools/luac_decrypt.py
TOOL_NAMES = [
    "inspect_kkwe_luac",
    "fix_kkwe_opcode",
    "decompile_kkwe_luac",
    "batch_decompile_kkwe",
]

def register(server):
    mcp = server.mcp

    @mcp.tool(name="batch_decompile_kkwe")
    def batch_decompile_kkwe(
        input_dir: str,
        output_dir: str,
        opcode_state: str = "auto",   # auto / kkwe / fixed
    ) -> dict:
        """批量反编译 KKWE Lua 字节码目录。
        input_dir: 存放 *.luac 的目录（绝对路径）
        opcode_state: auto=自动检测置换状态（推荐）
        返回: {success, total, ok, failed, output_dir}
        """
        return server.get_payload("batch_decompile_kkwe")(
            input_dir=input_dir,
            output_dir=output_dir,
            opcode_state=opcode_state,
        )
```

- **薄函数**：只透传参数给 payload，不写逻辑。
- **docstring 即智能体的使用手册**：参数含义、取值范围、默认行为、返回结构，全写在这里（详见 3.3）。

### 2.3 注册三件套（新工具不出现在客户端的根因）

**本项目真实踩坑**：新增工具模块后只改了 `mcp_tools/`，忘了接另外两处，工具静默不暴露，排查浪费大量时间。新工具必须同时改 3 处：

| # | 位置 | 作用 | 漏掉的后果 |
|---|---|---|---|
| 1 | `mcp_tools/__init__.py` 的 `REGISTERED_TOOL_MODULES` | 模块被加载 | 工具完全不注册 |
| 2 | `server.py` 的 `_LAZY_IMPORTS` | payload 可被懒加载 | 注册了但调用时报 payload 不存在 |
| 3 | `registry/tool_catalog.py` 的可见集 | 工具在某个 surface 可见 | 注册了但客户端 list 不到 |

**建议固化成检查清单**（写进本仓库的验收流程）：

```text
□ 工具模块文件 + TOOL_NAMES
□ REGISTERED_TOOL_MODULES 追加模块名
□ _LAZY_IMPORTS 注册每个 payload
□ tool_catalog 加入目标可见集（含别名）
□ health_report 工具总数 +N
□ 客户端实际 list 到该工具（光看服务端日志不算数）
```

### 2.4 能力层模块划分原则

1. **按领域切，不按调用频次切**：`objects/`、`terrain/`、`scripting/`、`resources/`、`runtime/`、`validation/`……每个子包有明确的"这个领域的所有实现"边界。
2. **通用逻辑进 core，类型特定逻辑进上层管线**：例如"刷地表"是通用原语放 `core/terrain/`，"侏罗纪生存地图该用哪套地表主题"放 `map_types/survival_core/`。子包不应重复定义通用原语。
3. **兼容 shim 只减不增**（见 1.2）。
4. **跨领域编排放专用编排层**（如 `production/`、`refactor_engine/`），不塞进单一领域子包。

### 2.5 目录骨架（可直接套用的模板）

```text
<name>_mcp/
├─ server.py              # 门面：FastMCP 实例 + 装配（薄）
├─ config.py              # 环境变量与路径配置，启动时一次性解析
├─ paths.py               # 路径安全解析（白名单/穿越防护）
├─ mcp_tools/
│  ├─ __init__.py         # REGISTERED_TOOL_MODULES 注册表
│  ├─ _registration.py    # 统一的注册 boilerplate（抽公共样板）
│  └─ <domain>.py         # 薄封装 × N
├─ core/
│  ├─ <domain>/           # 能力子包 × N
│  ├─ validation/         # 门禁与校验
│  ├─ integrations/       # 外部程序适配
│  └─ registry/           # 工具目录/成熟度/可见性
├─ res/                   # 静态数据快照（不依赖运行时源）
├─ tests/                 # 每个工具模块至少 1 个测试文件
└─ start_mcp.cmd / __main__.py
```

## 3. 工具设计契约（智能体视角）

### 3.1 命名纪律

| 规则 | 好 | 坏 | 原因 |
|---|---|---|---|
| `动词_名词` snake_case | `create_unit_from_prompt` | `unitCreation` | 智能体靠名字选工具 |
| 动词精确到操作类型 | `inspect_*`（只读）/ `validate_*`（校验）/ `apply_*`（写入）/ `cleanup_*`（清理） | 全用 `do_*` / `handle_*` | 前缀即风险等级，见 3.5 风险分级 |
| 同前缀同语义 | 所有 `validate_*` 都是只读门禁 | 一个 `validate_x` 顺手写了文件 | 智能体基于前缀形成安全预期 |
| 避免近义混淆 | 一个动作一个名字 | `get_user` + `fetch_user` 并存 | 智能体会随机选 |
| 别名走注册表，不进代码 | `extract_rpg_defense_profile` 别名 `extract_defense_profile`，由 catalog 统一管理 | 代码里注册两个函数 | 别名爆炸时无法审计 |

### 3.2 参数设计

1. **每个参数必须有 description**：含义 + 取值范围 + 缺省行为。这不是注释，是智能体的使用手册。
2. **可枚举的必须枚举**：`opcode_state: "auto" | "kkwe" | "fixed"`，并在描述里解释每个值何时选。
3. **可选参数必须有安全默认值**：`overwrite: bool = False`（不覆盖）、`limit` 给上限。危险默认值（如 `overwrite=True`）是事故来源。
4. **路径参数必须声明是绝对路径还是相对路径**，以及相对什么根（本项目所有路径参数声明"绝对路径"，由 `paths.py` 统一白名单校验）。
5. **分页参数成对出现**：`offset` + `limit`（带默认上限，如 100，防单次返回撑爆上下文）。
6. **参数数量控制**：一个工具参数超过 8 个就要反思是不是该拆。20 参数的万能工具不如 5 个专注工具。

### 3.3 docstring 标准结构

```text
<一句话：这个工具做什么>
<输入约定：关键参数的取值/格式/根目录>
<行为：写入还是只读？是否可重复执行？默认输出到哪>
<返回结构：主要字段含义>
<前置条件与后续建议：先跑什么、跑完该跑什么（门禁）>
```

例（本项目风格）：

```text
批量反编译 KKWE Lua 字节码目录。
input_dir: 存放 *.luac 的目录（绝对路径）
output_dir: 反编译结果目录，不存在自动创建
opcode_state: auto=自动检测置换状态（推荐，两种输入都能吃）
返回: {success, total, ok, failed, output_dir, failures:[{file, error}]}
前置: 建议先对单文件跑 inspect_kkwe_luac 确认格式。
```

### 3.4 返回值契约

1. **统一信封**：一切返回都是 dict，`success: bool` 必在首位；失败时带 `error` + `suggestion`（下一步做什么）。
2. **机器数据用 JSON，人类解释用 Markdown 文本**，不要混。
3. **批量操作必须给汇总 + 明细**：`{total, ok, failed, failures:[{file, error}]}`——只回"全部成功/失败"等于没回。
4. **大结果分页或截断**，并显式返回 `truncated: true` 与总数，别让智能体以为拿到了全量。
5. **写操作必须回"改了什么"**：影响文件列表、快照路径、可逆性说明。
6. **诊断类工具返回结构化错误码**（见 6.3），错误码是稳定契约，文字描述可以改，码不能改。

### 3.5 工具风险分级（本项目四分类，通用适用）

| 分类 | 语义 | 示例前缀 | 暴露与闸门策略 |
|---|---|---|---|
| `direct` | 只读检查、分析、预览 | `get_*` `list_*` `inspect_*` `analyze_*` `validate_*` `read_*` | 全 surface 可见，无闸门 |
| `distortion_risk` | 写入/生成内容，可污染工程 | `create_*` `apply_*` `place_*` `paint_*` `build_*` | 执行后**必须**建议跑对应门禁 |
| `external` | 依赖外部程序/资源（CLI、引擎、真实文件） | `compile_*` `convert_*` `launch_*` | 健康检查要报告依赖是否就绪 |
| `gate_only` | 删除、编译发行、注入、启动等高危 | `delete_*` `compile_release_*` `inject_*` `launch_*` | 仅专家面可见；要求先存快照；文档显式标红 |

**surface（可见面）机制**：按使用方分暴露面（如 `trae` 窄面给 AI 助手、`ide` 专家面给熟练用户），窄面只给"高层入口 + 只读诊断"。**工具多不是资产，AI 选得准才是资产**——477 个目录项对 AI 只暴露 20 个。

### 3.6 高层入口 vs 底层工具

给 AI 的使用路径设计**编排入口**，而不是让 AI 自己拼底层调用：

```text
高层入口（AI 首选）:  drive_map_production   ← 一个调用内部编排多步
底层专家工具（人工/专家面）: create_unit / paint_terrain / inject_trigger ...
```

编排入口负责：判断新建/续作、选择路径、在每步后自动跑门禁、失败时给出 `explain_next_actions`。底层工具留给明确知道自己在做什么的使用者。**两条路径都要能走通同一件事**，否则编排入口是假的。

## 4. 错误处理与失败契约

### 4.1 三层错误模型

```text
L1 参数错误   → 不进业务逻辑就返回：success:false + 哪个参数 + 期望什么
L2 业务错误   → ToolError(错误码, 信息, suggestion)：稳定错误码 + 修复方向
L3 系统错误   → 兜底捕获：不外泄堆栈，回 {success:false, error:可读摘要, log_ref}
```

- **不裸抛异常**：MCP 工具里未捕获异常 = 客户端拿到一坨 traceback，智能体无法操作。
- **错误码是稳定契约**：`missing_ability_reference`、`empty_war3map_doo` 这类码写进文档，修复逻辑和智能体都靠码路由，不靠解析中文句子。
- **suggestion 必须是可执行的下一步**："`table/unit.ini` 的 `abilList` 引用的技能不存在，先 `create_ability` 或修 `abilList`"——不是"请检查配置"。

### 4.2 失败分类（failure_category）模式

对外部程序（编译器、转换器）返回非零或输出异常时，**先分类再暴露**，别让原始日志直接糊给智能体：

```text
原始错误 ──> failure_category 分类 ──> 每类一个"首要处理方向"
```

本项目 `compile_map` 的分类表（通用范式）：

| failure_category | 含义 | 首要处理 |
|---|---|---|
| `*_config_error` | 配置/导入表问题 | 检查配置文件与路径 |
| `*_script_error` | 脚本/代码错误 | 检查最近生成的脚本 |
| `*_content_error` | 数据损坏 | 检查最近改过的数据文件 |
| `*_output_package_error` | 返回码成功但产物结构错 | 校验输出包结构，别先改业务代码 |

**排查顺序要写进文档**：`preflight 检查 → 分类 → 领域日志 → stdout/stderr → 最后才怀疑工具链本身`。智能体最常见的错误就是"一失败就怪工具坏了"。

### 4.3 "退出码 0 ≠ 成功"

外部程序返回 0 只表示进程没崩，**产物本身还要独立校验**：

```text
compile 返回 0
  └─> 校验输出包是否含关键文件（结构校验）
        ├─ 通过 → 成功
        └─ 不通过 → 报 compiler_output_package_error，禁止当成功交付
```

通用化：任何"生成产物"的工具（打包、导出、转换），都必须对产物做**存在性 + 关键结构**校验，而不是信任退出码。

### 4.4 幂等与可重入

1. **读工具必须幂等**：同样输入两次调用结果一致（不要掺时间戳、随机数进返回）。
2. **写工具要声明可重入性**：重复执行是"覆盖"还是"追加"？本项目解包工具约定"只写输出目录、不碰工程、可重复、可覆盖"——这句话必须写进 docstring。
3. **状态检测优于状态假设**（本项目最典型的修复）：batch 反编译曾对"已还原过的输入"再还原一次导致 60/60 全炸（双重还原）。解法不是要求调用方保证输入状态，而是工具**自检输入状态**（`detect_opcode_state`：按末尾指令特征判断 stored/fixed），fixed 输入自动跳过还原。
   - 通用规则：**工具能吃下它可能遇到的每一种合法输入状态**，用检测而不是假设。
4. **快照 + 回滚是写闸门的标配**：`gate_only` 操作前生成快照（`save_project_snapshot_tool`），提供 `rollback_*` 路径。

## 5. 安全设计

### 5.1 输入边界（一切外部输入都不可信，智能体也是外部）

智能体会 hallucination，因此**智能体传入的参数必须按不可信输入处理**：

| 输入类型 | 风险 | 必须做的校验 |
|---|---|---|
| 路径 | 路径穿越、写穿工作区 | 统一 `paths.py` 白名单：只允许工作区/server 根/指定外部根之内；拒绝 `..`；解析后二次确认 real path 在根内 |
| 枚举参数 | 非法取值进业务逻辑 | 显式白名单匹配，非法值直接 L1 错误 |
| 大整数/尺寸 | 内存爆炸 | 上限校验（limit、size 给硬上限） |
| 脚本/代码字符串 | 注入 | 进入目标格式前做语法级校验（本项目：JASS 先过 `scan_jass_symbols` + 引用校验再落盘） |
| 对象/资源 ID | 引用悬空 | **数据源以工程自身为真相**：ID 必须能在工程表或内置目录解析到，解析不到就拒绝，绝不编造 |

**本项目铁律（通用化）**："不编造对象数据" —— 所有引用型 ID 必须先 `resolve`/`search` 再 `apply`。这条规则挡掉了 WE 打不开的头号事故源。

### 5.2 配置与密钥

1. **密钥/凭据只从环境变量进**，绝不进参数描述、日志、错误信息。
2. **路径类配置启动时一次性解析**（`config.py`），运行时不重复解析、不信任调用方传的"配置"。
3. **默认值要显式且安全**：未设置 `WAR3_MCP_SURFACE` 时默认窄面（最小暴露），而不是全量面——**默认最小权限**。
4. **健康检查报告依赖就绪状态**：外部程序（CLI、Java、游戏引擎）缺失时，health 报告明确标出，而不是调用时才炸。

### 5.3 写操作闸门（gate_only 的三道闸）

```text
第一道  暴露面闸：高危工具不在窄面暴露（AI 助手根本 list 不到）
第二道  前置闸  ：要求先存快照 / 先跑门禁（docstring 写明，代码里可强制）
第三道  产物闸  ：产物结构独立校验（见 4.3），失败不交付
```

### 5.4 子进程安全

封装外部 CLI 时：

- 参数**列表传参**，不拼 shell 字符串（防注入）；
- 捕获超时（外部程序挂死不能拖死 MCP 进程）；
- stdout/stderr 截断保留（大日志只留头尾 + 错误行，全量写 log 文件给引用）；
- 退出码 + 输出**双证据**判断成功（见 4.3）。

### 5.5 输出安全

- 不把本机绝对路径回显进返回（除非必要）；
- 不把密钥、token 片段带进错误信息；
- 大文本输出（反编译源码、日志）走文件 + 返回路径，不直接塞进响应撑爆上下文。

## 6. 验证与质量门禁

### 6.1 为什么门禁必须独立成层

把"校验"揉进写工具内部，会有三个后果：智能体写完后忘记校验（写工具只回"写成功了"）、校验逻辑无法单独复用、错误无法统一归类。**本项目经验：写入类工具执行后必须建议跑对应门禁，并把这条写进 docstring 的"后续建议"。**

### 6.2 门禁分层（由轻到重）

```text
L1  单点校验   validate_object_fields        单个对象/单条记录合法吗
L2  引用校验   validate_jass_symbol_references  跨文件引用是否悬空
L3  资源校验   validate_project_resources    资源存在 + 路径合法 + 导入表一致
L4  综合门禁   validate_<domain>_quality_gate 工程级：文件齐全/尺寸一致/引用闭环/可打开风险
L5  产物校验   compile + 输出包结构校验       最终产物独立验证（不信任退出码）
```

每层都是**只读**、幂等、返回 `{success, issues:[{code, location, message, fix_hint}], summary}`。

### 6.3 错误码体系（稳定契约）

```text
错误码命名:  <对象>_reference 悬空引用 / <对象>_missing 缺失 / <对象>_invalid 非法 / <对象>_duplicate 重复
例:
  missing_ability_reference        → 修 unit 的 abilList，或先创建该 ability
  empty_war3map_doo                → 重新跑生成工具写入真实实例，别补空白占位
  invalid_path_traversal           → 路径白名单拒绝
```

**规则**：
1. 一个错误码对应**唯一首要修复方向**（写进文档表），智能体按码路由修复；
2. 码一旦发布就不能复用/改义，只能新增；
3. `repair_*` 类自动修复工具**必须声明它处理哪些码**，处理不了的明确返回"需人工"。

### 6.4 推荐修复顺序（写进文档，让智能体照单执行）

```text
1. cleanup_invalid_*      先清悬空引用
2. sync_*_from_*          再同步派生数据（如 pathing from terrain）
3. validate_*_table       表级校验
4. validate_project_resources  资源级
5. validate_symbol_references  脚本级
6. validate_<domain>_quality_gate  综合门禁
7. compile / compile_release_candidate
8. 实机验证（若可用）
```

### 6.5 诊断上下文工具（builder console 模式）

多步骤生产流程中，智能体跨会话继续工作时**没有记忆**。本项目用一个纯文本 "builder console" 承载：质量门禁结果、编译日志摘要、人工备注、下一步建议。配套工具：`read_builder_console` / `write_builder_console_note` / `run_builder_console_diagnostics`。

**通用价值**：任何多轮、跨会话的任务型 MCP，都应该有一个**外置的、人类可读的**任务状态文件 + 读写工具，而不是指望智能体自己记。

### 6.6 反"假成功"验证法（来自逆向实战，适用于一切解析/转换工具）

**判断"解析/转换是否正确"，不要问"能不能跑完"，要问"产物里有没有真实内容"。**

本项目两次栽在"假成功"上：
1. 解析器"跑完且终点贴合文件尾"，但常量数恒为 0 —— 解析假设是错的，产出的 16 个文件全是错的；
2. 字节码"能反汇编"，但指令流是 `LE/ADD/SETUPVAL` 这种不可能的序列 —— 其实是解析器对齐错了，不是数据加密。

**对策（做成工具的内建自检）：**

| 手段 | 说明 | 案例 |
|---|---|---|
| 内容合理性断言 | 解析产物必须含"预期类型的真实内容"，空/零值直接判失败 | 常量表非空、opcode 合法率 > 阈值 |
| 独立路径交叉验证 | 写第二个**完全独立代码路径**的验证器 | JASS 反混淆用"随机代入等价性验证器"交叉验证 1193 行，0 处不等价才敢交付 |
| 状态分布自检 | 产物统计应符合已知分布 | opcode 还原后 MOVE/LOADK/CALL/RETURN 从 0 次恢复到万级，分布回归标准形态 |
| 黄金样本回归 | 每次改动跑已知正确答案的样本 | 解密器对 3 张已知地图（标准/KKWE混淆/大包）回归验收 |
| 可重入自检 | 工具对自己处理过的输出再跑一遍应安全（幂等或明确报错） | `detect_opcode_state` 识别已还原输入，防双重还原 |

## 7. 外部程序集成（integrations 层）

MCP 服务器常常要驱动外部程序（编译器、转换器、CLI、DLL、引擎）。本项目的 w2l 编译器、warcraft-rs BLP 转换、unluac（Java jar）都是这类。集成层的设计目标：**外部程序的接口变化、版本漂移、环境缺失，都被隔离在这一层，业务层无感。**

### 7.1 适配器模式

```text
core/integrations/
├─ <external_tool>.py     # 一个外部程序一个适配器
│   - locate()            # 探测可执行文件位置（多候选 + 环境变量覆盖）
│   - version()           # 版本探测与兼容判断
│   - run(args, timeout)  # 统一执行：列表传参 / 超时 / 输出截断 / 退出码+输出双证据
│   - available()         # health 检查调用
```

**本项目 Java 探测顺序（通用范式）**：

```text
显式参数 > 环境变量 JAVA_HOME > PATH 查找 > 常见安装目录逆序扫描（JDK21 → 旧版）
```

要点：
1. **每个外部依赖都有"探测链"**，探测结果进 health_report（缺了什么、在哪找的、怎么补）；
2. **可执行文件位置可被环境变量覆盖**（`WAR3_W2L_EXE`、`WAR3_JAVA`……），写进配置文档；
3. **jar/动态库类依赖随仓库分发**（`res/luac/unluac.jar` 入库，332KB），发行包不依赖用户环境里恰好有它；
4. **外部程序输出是数据不是命令**：解析其输出时按容错解析（截断、缺字段、乱码都不许崩，返回带 `parse_warnings`）。

### 7.2 何时该用"纯本地复现"替代外部程序

本项目关键决策：**KKWE 解密最终纯 Python 实现，放弃了直调 StormLib.dll 路线**（32 位 DLL 需要 32 位 Python 环境，链太长）。判据：

```text
外部程序调用链长度 × 环境脆弱度  >  自研复现成本  →  自研复现
```

- 密码学算法（标准 StormLib 加密）**本来就是公开的**，复现成本极低 → 纯 Python 一行依赖都没有；
- 复现后还要**拿真实样本回归**证明等价（3 张地图全解对才算数）。

### 7.3 依赖缺失的优雅降级

- 依赖缺失时工具**仍可加载**，调用时返回 `{success:false, error:"依赖未就绪", suggestion:"如何安装/配置"}`；
- 绝不在 import 阶段 import 缺失依赖导致整个 server 起不来——**懒加载 + 运行时检查**是硬要求。

## 8. 静态数据快照（res/ 层）

MCP 工具经常需要外部知识库（内置对象目录、API 元数据、模板注册表）。**运行时去源仓库拉数据是灾难**：源一改行为就变、离线环境直接失效。

本项目模式：

```text
res/
├─ ydwe/ydwe_jass_index.json        # YDWE API 索引快照（从源码构建一次，入库）
├─ ydwe/ydwe_template_registry.json # 模板注册表快照
├─ luac/unluac.jar                  # 反编译器本体
└─ w3x2Ini2.7.3/                    # 编译器与内置数据
```

规则：
1. **快照入库**：构建脚本（`rebuild_*_index` / `build_*_registry`）只在开发环境跑，产物 `*.json` 提交进仓库，发行包直接带；
2. **运行期只读快照**，并暴露 `source_mode=resource_snapshot` 让使用方知道数据从哪来；
3. **更新快照是显式动作**（跑 rebuild 工具 → diff → 提交），不是隐式的；
4. **快照要能自检**：`get_*_index_status` 报告快照版本、条目数、构建时间。

**通用化**：任何"工具行为依赖外部数据"的场景，都问一句——"这些数据能否冻结成快照？运行期还需要活源吗？"不需要就冻。

## 9. 客户端接入与启动

### 9.1 启动脚本的坑（真实事故）

| 坑 | 现象 | 解法 |
|---|---|---|
| `mcp.json` 里 `command` 写裸名 `python` | 系统 PATH 无 python → 客户端拉起 MCP 直接失败，且**客户端侧报错极难排查** | **绝对路径**写进 mcp.json |
| 环境变量依赖客户端注入 | `WAR3_EXE_PATH` 等没配 → 部分工具静默不可用 | 健康检查报告依赖状态；启动脚本里给默认值 |
| 启动脚本不设置关键默认面 | 默认窄面 vs 专家面行为差异大，用户困惑 | `start_mcp.cmd` 显式 `set WAR3_MCP_SURFACE=ide`，并在 README 写明两个入口的行为差异 |
| 命名管道/IPC 连通性误判 | `netstat` 查不到命名管道（它不是 TCP），误以为桥接没起 | 用 API 探测管道（`win32file.CreateFile`）判断，别靠 netstat |

### 9.2 mcp.json 配置模板

```json
{
  "mcpServers": {
    "<your-tool>": {
      "command": "<绝对路径/启动脚本 或 可执行文件>",
      "args": [],
      "env": {
        "<依赖路径类变量>": "<绝对路径>"
      }
    }
  }
}
```

**纪律**：
1. `command` 一律绝对路径（启动脚本也是）；
2. `env` 只放路径类与开关类变量，**不放密钥**（密钥走系统级环境变量）；
3. 改完配置需要**重启 MCP 连接器**才生效——写进 README，避免"改了没生效"类困惑。

### 9.3 启动即自检

CLI 入口（`__main__.py` / `run_server.py`）提供**不依赖客户端**的自检命令：

```text
--version   版本
--health    全依赖健康检查（外部程序/快照/路径）
--smoke     冒烟测试（走一遍关键工具，--smoke-dry-run 不落盘）
```

**价值**：客户端连不上时，先本地跑 `--health` 把"是配置问题还是服务问题"分开——这是本项目排障效率最高的设计之一。

## 10. 测试策略

### 10.1 测试金字塔（MCP 版）

```text
           ┌────────────────────────┐
           │ L3 真实智能体端到端     │  让 AI 跑完整任务，观察工具选择是否合理
           ├────────────────────────┤
           │ L2 工具集成测试         │  每个工具正常/异常路径（unittest/pytest）
           ├────────────────────────┤
           │ L1 核心逻辑单测         │  解析器/算法/校验器纯函数单测
           └────────────────────────┘
```

- **L1 是性价比最高的**：本项目逆向工具（MPQ 解密、字节码解析、JASS 反混淆）的核心都是纯函数，单测覆盖"黄金样本 + 边界输入"就能挡住绝大多数回归。
- **L2 每个工具模块至少 1 个测试文件**（本项目 `tests/` 与 `mcp_tools/` 基本一一对应），必测路径：正常、缺参、非法枚举、路径越界、依赖缺失。
- **L3 用真实智能体跑**：看起来对但让智能体困惑的工具就是有 bug。验收标准之一是"智能体选对工具"，不是"工具能跑"。
- **冒烟测试进 CLI**（`--smoke --smoke-dry-run`）：不依赖客户端，发布前必跑。

### 10.2 测试数据管理

1. **黄金样本入库（小样本）或固定路径（大样本）**：已知正确答案的输入输出对，每次改动回归；
2. **大文件样本不进 git**（几十 MB 的地图/字节码 dump），用文档记录路径与获取方式，CI/验收脚本检查存在性；
3. **测试工程与真实工程隔离**：写路径统一落 `test_work/` 沙盒，禁止测试写真实工程。

### 10.3 改动后的最小验收链（写进仓库 README，强制执行）

本项目标准验收命令（任何源码/文档改动后）：

```text
1. 语法级     compileall（或 tsc --noEmit / cargo check）
2. 目录回归   工具目录测试（注册三件套是否对齐）
3. 健康检查   python -m <pkg> --health
4. 冒烟       python -m <pkg> --smoke --smoke-dry-run
5. 受影响领域 对应 validate_* 门禁跑通
```

**规则：验收链未跑完，改动不算完成。**（对应项目纪律："每次开发完毕一个功能或模块后，必须认认真真做一次验收测试和整体代码验收审查，不得影响原有功能。"）

### 10.4 回归风险判断（blast radius 思维）

改一个公共模块前，先问：

```text
1. 谁在 import 它？（依赖方清单）
2. 它属于哪一层？（改 L1/L2 比改 L5/L6 风险低一个量级）
3. 哪些黄金样本会经过它？（跑回归）
```

门面层（server.py）、注册表（tool_catalog）、路径层（paths.py）是**最高频被依赖**的三处，改动它们必须跑全量冒烟。

## 11. 可观测性（日志与诊断）

### 11.1 日志分层

| 层 | 内容 | 去向 |
|---|---|---|
| 调用日志 | 每次工具调用：工具名、耗时、参数摘要、success/failure | 结构化日志文件（`logs/`），不进响应 |
| 领域日志 | 外部程序 stdout/stderr 全量、门禁逐条 issue | 日志文件，响应只给摘要 + 文件引用 |
| 诊断上下文 | 跨轮任务状态、修复历史、下一步建议 | builder console（见 6.5），给智能体读 |

### 11.2 诊断设计三原则

1. **失败响应自带"排查路线图"**：`preflight_validation → failure_category → diagnostic_summary → 原始日志引用`，按此顺序暴露，不让智能体从原始日志大海捞针；
2. **错误摘要分层截断**：原始日志 10MB 时，响应给"错误行 ± 上下文 + 总行数 + 文件路径"；
3. **health 是全依赖的单一入口**：一条 `health_report` 回答"现在能不能干活"（版本、依赖就绪、快照状态、配置来源、工具计数）。

### 11.3 成熟度/能力状态工具

本项目 `get_core_maturity_status` / `list_core_maturity`：各子领域成熟度（可用/实验/废弃）的注册表 + 查询工具。**通用价值**：工具面大时，暴露"哪些能力是稳定的、哪些是实验性的"，让智能体（和人）知道边界，避免拿实验功能当生产用。

## 12. 开发流程（标准作业程序）

### 12.1 新功能/新工具 SOP

```text
阶段 1  需求与文档先行
  □ 先翻既有技术文档/分析文档，确认依赖的接口/格式真实可用（项目铁律：不瞎写代码）
  □ 明确：工具名（3.1 纪律）、风险分级（3.5）、暴露面、前置/后置门禁

阶段 2  接口设计
  □ 参数 schema + docstring（3.2/3.3 标准结构）
  □ 返回信封 + 错误码（3.4 / 6.3）
  □ 检查：陌生人只看名字和描述能否正确调用

阶段 3  实现
  □ 实现进能力层子包，注册层保持薄函数
  □ 外部依赖走 integrations 适配器（7.1）
  □ 写操作接快照/回滚（5.3）

阶段 4  注册三件套（2.3 清单，逐项打勾）

阶段 5  测试
  □ L1 单测（黄金样本 + 边界）
  □ L2 工具集成测试（正常/缺参/非法值/越界/缺依赖）
  □ 验收链（10.3）全跑通

阶段 6  文档回写（项目铁律）
  □ README 工具表 + 环境变量表
```

### 12.2 排障 SOP（工具"不工作"时）

```text
1. 本地自检        python -m <pkg> --health          → 服务/依赖是否就绪
2. 客户端配置核查   command 绝对路径？env 齐全？改后重启连接器？
3. 可见性核查      该工具在当前 surface 的可见集里吗？（list_tool_catalog）
4. 注册三件套核查   三处是否都对齐？（2.3）
5. 工具级诊断      直接 CLI/测试里调该工具，看 success:false 的 suggestion
6. 领域日志        日志文件全量输出（11.2 的引用路径）
```

**纪律：按顺序来。最常见的事故在 2/3/4 步（配置/可见性/注册），却最容易被跳过——大家总想直接怀疑代码。**

### 12.3 代码质量红线（项目纪律的通用化表述）

1. **不叠加屎山**：模块分离、职责单一；发现自己在往大文件里加第 N 个无关功能时，先拆再写。
2. **稳健性优先于功能量**：宁可少一个功能，不可埋一个悬空引用（6.3 错误码体系存在于此目的）。
3. **每个功能完成 = 验收测试 + 整体审查 + 文档回写**，三者缺一不算完成。
4. **影响原有功能 = 事故**：新工具上线后，全量冒烟 + 关键黄金样本回归是强制项。
